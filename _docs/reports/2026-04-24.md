# WalletChan Browser Extension Security Review

Date: 2026-04-24

Scope: Browser extension wallet security review focused on malicious dapps, private-key/API-key safety, browser-extension attack surfaces, wallet confirmation integrity, and all wallet types:

- Bankr API accounts (`type: "impersonator"` / `type: "bankr"` paths)
- Private key accounts (`type: "privateKey"`)
- Seed phrase accounts (`type: "seedPhrase"`)

No code changes were made during this review.

## Executive Summary

The extension has several release-blocking issues. The most important pattern is that dapp-controlled metadata crosses the `window.postMessage` / content-script boundary and is later treated as trusted confirmation context. Pending requests do not snapshot the account, tab, signer, and chain at request creation time; confirmation then signs or submits using whichever account is current at confirmation time.

There are also agent-password boundary issues after MV3 service worker restart, and `impersonator` accounts are documented as view-only but are treated as Bankr-capable in batch execution paths.

## Findings

### Critical: View-only `impersonator` accounts can execute through batch paths

**Status: VALID** — The UI promises view-only in `AddAccount.tsx:574` ("View-only, no signing") and `AddAccount.tsx:892-893` ("View-only mode: You can view transactions and signatures but cannot sign or send"). `TokenTransfer.tsx:452-460`, `Swap/SwapView.tsx:629`, and `sponsoredTransferHandlers.ts:95-96` all enforce this. But the ERC-5792 batch, cross-dapp batch, swap-direct, and normal `eth_sendTransaction` confirm paths do not — they treat impersonator as a Bankr account. If the user also has a Bankr account cached, the Bankr API signs with the Bankr key's owner address — so a tx approved on the impersonator account would submit from the wrong signer. `CLAUDE.md:15` is stale (describes 3 account types when the codebase has 4). Fix: enforce view-only across all remaining execution entry points and correct `CLAUDE.md`.

`impersonator` accounts are documented as view-only in `apps/extension/src/chrome/accountStorage.ts:171`, but batch and cross-dapp batch paths treat them as Bankr-capable:

- `apps/extension/src/chrome/batchTxHandlers.ts:140`
- `apps/extension/src/chrome/batchTxHandlers.ts:202`
- `apps/extension/src/chrome/crossDappBatchHandlers.ts:75`

Impact: An account type that should not hold signing authority can reach execution-capable flows. This is release-blocking.

Recommendation: Decide whether `impersonator` is truly view-only or a Bankr API account. If view-only, remove it from all execution, batching, capability, swap, and sponsored-transfer paths. If it is execution-capable, rename/re-document the type and enforce the same authentication and signer-binding rules as Bankr API accounts.

### Critical: Agent-password guards are bypassable after MV3 service worker restart

**Status: VALID** — Confirmed. `authHandlers.ts:432` checks `getPasswordType() === "agent"` before calling `tryRestoreSession`. After an MV3 SW restart, `cachedPasswordType` is `null`, so the guard returns false (not agent), the handler proceeds, and only then does session restoration fire inside the password-cache path — possibly populating the password type to `"agent"` *after* the guard already passed. Same pattern at `background.ts:1067, 1129, 1497, 1535, 2145`. Fix: centralized helper that restores session first, then evaluates the guard.

`cachedPasswordType` is memory-only and starts as `null`; it is restored only when session restoration runs:

- `apps/extension/src/chrome/sessionCache.ts:21`
- `apps/extension/src/chrome/sessionCache.ts:341`

Several master-only handlers check `getPasswordType() === "agent"` before restoring the session type:

- `apps/extension/src/chrome/authHandlers.ts:431`
- `apps/extension/src/chrome/background.ts:1063`
- `apps/extension/src/chrome/background.ts:1168`
- `apps/extension/src/chrome/background.ts:1497`
- `apps/extension/src/chrome/background.ts:1535`
- `apps/extension/src/chrome/background.ts:2145`

Impact: After an agent unlock with auto-lock set to "Never", a service worker restart can leave the password type unknown. Master-only operations can pass the guard before session type is restored.

Recommendation: Add a centralized helper for master-only operations that restores or loads password type first, then rejects agent sessions before side effects. Use it for API key changes, account imports, account removal, reset, and other destructive/sensitive operations.

### High: Transaction and signature requests are not bound to originating account/tab/signer

**Status: VALID (pervasive)** — Pending tx/sig storage does not snapshot the account/tab/origin/chain at request creation. Confirm handlers resolve the currently-active account at confirmation time, so a user can receive a request on account A, switch to account B, and unknowingly sign with B. Fix requires storage-shape changes plus rewrites in every confirm handler. Deferred to last because of blast radius.

Pending request storage does not snapshot the account, account address, account type, tab ID, frame/origin, or trusted chain context:

- `apps/extension/src/chrome/pendingTxStorage.ts:8`
- `apps/extension/src/chrome/pendingSignatureStorage.ts:19`
- `apps/extension/src/chrome/txHandlers.ts:149`
- `apps/extension/src/chrome/txHandlers.ts:190`

Confirmation later resolves the current active/tab account:

- `apps/extension/src/chrome/txHandlers.ts:1001`
- `apps/extension/src/chrome/txHandlers.ts:1103`
- `apps/extension/src/chrome/batchTxHandlers.ts:567`

Local signing ignores dapp-supplied signer metadata and signs with the provided private key:

- `apps/extension/src/chrome/localSigner.ts:99`
- `apps/extension/src/chrome/localSigner.ts:197`

Impact: A user can receive a request for one account, switch accounts, and confirm with another. A malicious dapp can also spoof displayed `from` or signer params while the background signs with the current account. This affects Bankr API, private-key, and seed-phrase flows.

Recommendation: At request creation, resolve the trusted account from `sender.tab.id` and extension state, then store `accountId`, `accountAddress`, `accountType`, `tabId`, `origin`, and chain. Overwrite or reject dapp-supplied `tx.from` and signature signer params if they do not match. Confirmation must use the stored account, not `getActiveAccount()`.

### High: Page scripts can spoof bridge requests and signer metadata

**Status: VALID (overlaps with request binding)** — Content script trusts any same-window sender. The real defense needs to live in the background: schema-validate every dapp-originated message, bind to the trusted account/tab/origin at arrival (covered by the request-binding fix), and reject mismatched signer params.

The content script accepts same-window messages with only an `e.source === window` check:

- `apps/extension/src/chrome/inject.ts:227`

It forwards page-controlled transaction and signature data to the background:

- `apps/extension/src/chrome/inject.ts:421`
- `apps/extension/src/chrome/inject.ts:470`

Impact: Page scripts can bypass the intended inpage provider wrapper and craft `i_sendTransaction` / `i_signatureRequest` messages directly. The background currently relies too much on fields supplied through that untrusted channel.

Recommendation: Treat all content-script messages as untrusted. Background handlers should perform schema validation, account binding, signer validation, origin checks, size limits, and chain validation before saving any pending request.

### High: Signature UI can show one signer while another account signs

**Status: VALID** — The signature confirm UI displays the signer from `params[1]` (personal_sign) / `params[0]` (others) directly, while `localSigner.ts:197` calls `signMessage({ message: params[0] })` with whatever private key it was handed. A dapp can place an arbitrary-looking signer address in the params while the wallet signs with the currently-active account. Fix: validate signer param matches stored account address both at request-storage time and again at sign time. Best done alongside request binding; we'll add at-sign validation now and the at-storage binding in the request-binding pass.

The signature confirmation UI derives the signer from dapp-controlled params:

- `apps/extension/src/components/SignatureRequestConfirmation.tsx:70`

The local signer ignores those signer params and signs with the private key passed to it:

- `apps/extension/src/chrome/localSigner.ts:197`

Impact: A malicious dapp can display one signer address in the wallet UI while obtaining a signature from the currently selected account. This is especially dangerous for Permit2, EIP-2612, and other allowance-style signatures.

Recommendation: Validate signer params before storing and again before signing:

- `personal_sign`: `params[1]` must match stored account address
- `eth_sign`: `params[0]` must match stored account address
- `eth_signTypedData*`: `params[0]` must match stored account address

### High: Agent sessions can retrieve plaintext Bankr API key

**Status: VALID** — `getCachedApiKey` handler at `background.ts:1769` only checks `isExtensionPage(sender)`. The Change-API-Key screen (`AccountSettingsModal.tsx:178`, `ApiKeySetup.tsx:64`) calls it to prefill the existing key. An agent session can therefore read the plaintext Bankr API key — a long-term credential that signs arbitrary Bankr-API transactions. Private-key / mnemonic reveal paths are correctly master-only; this one slipped through. Fix: gate with `getPasswordType() === "master"` (after session restore), return `apiKey: null` for agent sessions.

`getCachedApiKey` is extension-page gated but not master-password gated:

- `apps/extension/src/chrome/background.ts:1769`

Impact: An agent session can restore and return the raw Bankr API key. If that API key is a custody or signing secret, this bypasses the intended agent-password restriction.

Recommendation: Make plaintext API key retrieval master-only, or replace it with non-secret status data for UI display.

### High: EIP-712 validation has DoS and chain-confusion gaps

**Status: VALID** — Needs verification of whether `eth_signTypedData` (v1) is even reachable (bridge may block it). The chainId-not-enforced angle is real: typed-data signing in `localSigner.ts` does not reject a domain.chainId that differs from the provider chain. Fix: enforce `domain.chainId` match and add size/depth limits in validator. Defer v1 reject until we've confirmed whether the inpage provider surfaces v1 at all.

Validation only covers `eth_signTypedData_v3` and `eth_signTypedData_v4`:

- `apps/extension/src/chrome/background.ts:561`
- `apps/extension/src/chrome/eip712Validator.ts:31`

`eth_signTypedData` still reaches signing:

- `apps/extension/src/chrome/localSigner.ts:211`

Typed-data signing receives `chainId` but ignores it:

- `apps/extension/src/chrome/localSigner.ts:167`

Impact: A malicious dapp can present one network in the wallet shell while signing typed data for a different domain chain. Validation also has recursive type-walking behavior that can be stressed by malicious schemas.

Recommendation: Validate all typed-data variants or reject deprecated variants. Enforce `domain.chainId` against the request/provider chain when present. Add total payload size, array length, field count, and iterative depth limits.

### Medium: Direct signing/broadcast handlers are not extension-only

**Status: VALID (defense-in-depth)** — The content-script bridge does not currently forward these names, so it's not exploitable today, but adding them to `EXTENSION_ONLY_MESSAGES` is a cheap defense in depth.

`EXTENSION_ONLY_MESSAGES` does not include direct execution handlers:

- `apps/extension/src/chrome/background.ts:476`
- `apps/extension/src/chrome/background.ts:2041`
- `apps/extension/src/chrome/background.ts:2051`
- `apps/extension/src/chrome/background.ts:2061`

These paths sign or broadcast without the normal dapp confirmation flow:

- `apps/extension/src/chrome/txHandlers.ts:1454`
- `apps/extension/src/chrome/sponsoredTransferHandlers.ts:129`

Impact: The current content-script bridge does not forward arbitrary names, but the background should enforce the trust boundary directly for defense in depth.

Recommendation: Add `executeSwapDirect`, `executeSwapBatch`, `sponsoredTransfer`, and other UI-only handlers to `EXTENSION_ONLY_MESSAGES`.

### Medium: Stale signatures and cross-dapp batches can outlive intended expiry

**Status: VALID** — Fix: re-check `Date.now() - timestamp > EXPIRY_MS` inside the confirmation handlers immediately before signing/submitting, both for signature requests and cross-dapp batches.

Signature confirmation checks existence but does not re-check timestamp:

- `apps/extension/src/chrome/txHandlers.ts:1098`
- `apps/extension/src/chrome/txHandlers.ts:1199`
- `apps/extension/src/chrome/pendingSignatureStorage.ts:29`

Cross-dapp batch confirmation does not enforce expiry:

- `apps/extension/src/chrome/crossDappBatchHandlers.ts:380`

Impact: Cleanup is best-effort and depends on service worker activity. A stale request can still be confirmed if it remains in storage.

Recommendation: Re-check expiry in every confirmation handler immediately before signing/submitting, including signature and cross-dapp batch flows.

### Medium: Malformed numeric and call fields can DoS UI or diverge from execution

**Status: PARTIALLY VALID** — Hardening the schemas is worthwhile but this is hygiene/DoS rather than a direct security bypass. Overlaps with the request-binding pass (where we add schema validation on request arrival). Deferred.

Several paths parse dapp-controlled numeric values with raw `BigInt` or lack request-time call limits:

- `apps/extension/src/components/TransactionConfirmation.tsx:408`
- `apps/extension/src/components/BatchTransactionConfirmation.tsx:1227`
- `apps/extension/src/chrome/gasEstimation.ts:114`
- `apps/extension/src/chrome/batchTxHandlers.ts:232`

Impact: Malformed `value`, gas, calldata, or batch payloads can crash confirmation UI, fill storage, or diverge between displayed and submitted values.

Recommendation: Add strict request schemas and size/count caps before storing pending requests. Reject invalid hex, decimal, address, calldata, value, gas, typed-data, and batch payloads.

### Medium: ERC-5792 bundle status is not origin-bound

**Status: VALID** — Fix: store owner origin with `BundleStatus` and require the `wallet_getCallsStatus` caller's origin to match.

Bundle status lookup is keyed only by bundle ID:

- `apps/extension/src/chrome/batchTxHandlers.ts:1017`
- `apps/extension/src/chrome/batchTxHandlers.ts:1042`

Impact: If a bundle ID leaks, another dapp can query status/receipts or trigger the explorer action.

Recommendation: Store owner origin/tab/frame with `BundleStatus` and require caller origin to match.

### Medium: Approval and signature-phishing coverage is incomplete

**Status: FEATURE GAP (not a bug)** — Adding more decoders is valuable UX but doesn't represent a bypass of any existing guard. Tracking separately; not fixed in this security-review pass.

Current approval decoding appears focused on ERC20 `approve`. The review did not find equivalent high-friction decoding/warnings for:

- ERC721 / ERC1155 `setApprovalForAll`
- ERC20 `increaseAllowance`
- EIP-2612 `permit`
- Uniswap Permit2 `PermitSingle` / `PermitBatch`
- Unlimited allowances
- Long deadlines
- Unknown spenders

Impact: These are common wallet-drainer vectors and may appear as ordinary calldata or typed data.

Recommendation: Add specialized decoders and warnings for approval-like calldata and typed-data signatures. Highlight spender, token, amount, deadline, verifying contract, and whether approval is unlimited.

### Low: Password change leaves stale session-restore password material

**Status: VALID** — `handleChangePassword` in `authHandlers.ts` clears in-memory caches but does not clear `chrome.storage.session`/`chrome.storage.local` session-restore material. Fix: clear session storage (or re-store with the new password) during password change.

Session restore stores encrypted password material:

- `apps/extension/src/chrome/sessionCache.ts:252`

Password change clears in-memory caches but does not clear or rewrite session storage:

- `apps/extension/src/chrome/authHandlers.ts:582`

Impact: Old password material remains recoverable by the extension until later cleanup.

Recommendation: Clear session restore storage after password change, or rewrite it with the new password only after explicit re-unlock.

### Low: Broad extension permissions increase attack surface

**Status: JUDGMENT CALL** — `file://*/*`, `http://*/*`, `all_frames: true` are all present. Wallet extensions typically need this breadth to provide EIP-1193 on every dapp, and changing it risks dropping wallet support on legitimate sites. Not treating this as an active bug; leaving for owner review.

Manifest permissions include all frames and broad file/http/https matches:

- `apps/extension/public/manifest.json:33`
- `apps/extension/public/manifest.json:54`
- `apps/extension/public/manifest.json:58`

Impact: This is common for wallet extensions, but it increases exposure to hostile frames and pages.

Recommendation: Remove `file://*/*` unless required. Consider whether `http://*/*` and all-frame injection are strictly necessary, and ensure frame/origin isolation is enforced where they remain.

## Positive Checks

- Secret-returning private key and mnemonic reveal paths are extension-page gated, restore session state before checking agent status, block agent sessions, and require supplied password validation.
- Crypto primitives use AES-GCM with random salt/IV and PBKDF2 600k iterations.
- The current content-script bridge forwards explicit inpage message cases rather than arbitrary background message types.

### Follow-up noted during phase A

- `handleWalletSendCalls` in `batchTxHandlers.ts` still uses `message.origin` (inject-derived) rather than `sender.origin` (Chrome-trusted) for the recorded bundle origin. Since both the write and read sides of the bundle-status check now use the same channel the attack surface is small, but tightening `wallet_sendCalls` to also use `sender.origin` is a free improvement. Folded into the phase E (request-binding) pass since that pass standardizes origin derivation across all dapp handlers.

## Recommended Fix Order

1. Remove execution capability from `impersonator` accounts or redefine the account type explicitly.
2. Centralize master-only/agent-password authorization and restore password type before checks.
3. Add trusted account/tab/origin/chain binding to all pending transaction, batch, and signature requests.
4. Validate dapp-supplied signer/from/chain fields against stored trusted state before storing and before signing.
5. Add strict schemas, size limits, and expiry enforcement for every dapp-originated request.
6. Move direct execution handlers behind the extension-only gate.
7. Expand typed-data, permit, Permit2, and approval-drainer warnings.
8. Revisit auto-lock "Never", session restore storage, and `chrome.storage` trusted-context access.
