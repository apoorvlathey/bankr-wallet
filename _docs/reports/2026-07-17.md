# WalletChan Passkey “Never Auto-Lock” Session-Restoration Security Audit

**Date:** 2026-07-17
**Scope:** Current uncommitted passkey/auth/session changes, including tracked, unstaged, and untracked files. Unrelated transaction-detail/UI changes were excluded unless they directly affected this security boundary.
**Method:** Independent manual source review, threat-model analysis, adversarial storage-failure reproduction, targeted tests, typecheck, lint, Chrome and Firefox builds, and read-only working-tree inspection. Semgrep was not used.
**Working-tree policy:** No code or documentation was changed during the audit itself. Nothing was staged, committed, stashed, reset, or otherwise altered.

---

## 1. Executive verdict

**Ship with fixes — do not release the audited tree unchanged.**

The cryptographic design is sound: no Critical or High-severity issue was found, no plaintext secret persistence was identified, passkey restoration cannot promote an agent session, and the restored general vault capability cannot reach the V2 mnemonic key or secret-reveal APIs. The principal residual risk is a concrete manual-lock failure: if both recovery-half deletion operations fail—or the UI never receives a successful lock result—the UI still presents the wallet as locked while a valid passkey Never session can remain restorable. The new “all wallet types” test also uses the view-only `impersonator` type as Bankr and bypasses production confirmation paths, so routine signing for all three real wallet types is not release-proven.

## 3. Detailed findings

### PKS-01 — Manual lock can leave a restorable session

#### Concrete code path

1. The UI sends `lockWallet`, but its callback unconditionally transitions to the locked screen without examining `chrome.runtime.lastError` or `response.success` at `apps/extension/src/App.tsx:3400`.
2. The router serializes the request at `apps/extension/src/chrome/background/authRouter.ts:268`.
3. Memory is synchronously cleared at `apps/extension/src/chrome/session/teardown.ts:11`.
4. The session ciphertext and local recovery key are removed concurrently with `Promise.all` at `apps/extension/src/chrome/session/persistence.ts:148`.
5. If both removals fail, both recovery halves survive. The router returns failure, but the UI still shows a successful lock.
6. A subsequent service-worker restoration decrypts the capability and restores routine signing caches.

This was reproduced with a valid private-key passkey Never session and injected failures for both `storage.session.clear()` and `storage.local.remove(sessionEncKey)`:

```json
{
  "lockRejected": true,
  "sessionStillPresent": true,
  "keyStillPresent": true,
  "restored": true,
  "signingKeyRestored": true
}
```

#### Threat actor and prerequisites

- A simultaneous browser/storage failure, extension-storage fault, or failed lock message.
- The browser session remains open.
- A later wallet query or request triggers restoration.
- This is not directly inducible by an ordinary webpage under the reviewed code.

#### Impact

- Restores the general vault capability as a master session.
- Bankr API cache and imported/derived signing keys can be restored.
- It does not restore the master password, PRF material, V2 mnemonic key, or seed phrase.
- Private-key and seed-phrase reveal still require explicit master-password proof.

#### Why existing checks and tests do not prevent it

The manual-lock test at `apps/extension/tests/session/passkeyNeverSession.test.ts:211` covers ordering on the success path. Storage-failure tests at `apps/extension/tests/session/passkeyNeverSession.test.ts:542` cover initial persistence, not teardown. The UI ignores both the response payload and runtime messaging errors.

#### Minimal remediation

- Attempt both revocations independently, preferably deleting the local recovery key first.
- Treat the session as securely revoked if either half is definitely gone.
- If both operations fail, return an explicit fatal lock failure and do not present the ordinary locked state.
- Make the UI honor `runtime.lastError` and `response.success`, display a retry/error state, and retry revocation.

#### Precise regression test

- Establish a valid passkey Never session.
- Inject failures for both recovery-key removal and session clear.
- Assert `lockWallet` reports failure and no successful locked event/UI transition occurs.
- Restore storage functionality, retry lock, simulate a fresh worker, and assert restoration fails.
- Repeat with only each individual operation failing; either single successful removal must make restoration impossible.

### PKS-02 — Incorrect Bankr fixture and shallow signing coverage

The new wallet loop uses:

- `impersonator`
- `privateKey`
- `seedPhrase`

at `apps/extension/tests/session/passkeyNeverSession.test.ts:41`.

The current repository type system defines:

- Bankr as `type: "bankr"` at `apps/extension/src/chrome/types.ts:22`.
- `impersonator` as a distinct view-only account at `apps/extension/src/chrome/types.ts:36`.

The test labels an impersonator `"bankr-account"` and supplies an encrypted API key at `apps/extension/tests/session/passkeyNeverSession.test.ts:73`. General hydration decrypts the API key independently of account type, so the assertion passes without exercising Bankr routing. Local wallet checks call `signMessage` directly at `apps/extension/tests/session/passkeyNeverSession.test.ts:178`, bypassing request intake, pinned-account authority, confirmation policy, final authorization, and broadcast/submission.

This also means the wallet-type definition in the supplied AGENTS instructions is stale relative to current source.

#### Impact

- No current authorization bypass was found through manual tracing.
- A future or existing Bankr/local confirmation regression could nevertheless ship while this test remains green.

#### Minimal remediation and regression test

- Use actual `bankr`, `privateKey`, and `seedPhrase` accounts.
- After cold restoration, execute a transaction and signature through the real pending-request and confirmation handlers.
- For Bankr, mock remote signing/submission and verify the pinned account and address.
- For private-key and seed-derived accounts, mock RPC broadcast and verify the recovered signer, pinned account, transport chain, and request terminalization.
- Add a negative `impersonator` case proving signing is rejected.

### PKS-03 — Session storage visibility is documented incorrectly

The implementation directly uses `chrome.storage.session` and does not change its access level. Chrome’s default is trusted extension contexts: service workers and extension-origin pages, but not content scripts. Therefore `_docs/IMPLEMENTATION.md` claiming it is “only accessible to the background service worker” is incorrect.

This does not expose the ciphertext to webpages or content scripts by default. Chrome documents session storage as memory-backed and hidden from content scripts by default; MDN describes the same lifecycle for Firefox:

- [Chrome Storage API](https://developer.chrome.com/docs/extensions/reference/api/storage)
- [MDN `storage.session`](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/storage/session)

#### Threat-model implication

- A compromised content script gets the random local half but not the ciphertext half.
- Arbitrary code execution in a trusted extension page can read both halves and recover the general vault capability.
- That prerequisite is already a serious extension-origin compromise, but raw key recovery is more powerful than merely interacting with background signing APIs.

#### Recommended remediation

- Correct the documentation and explicitly state that all trusted extension contexts are part of the secret-bearing trust boundary.
- If extension-page XSS is intended to remain outside that boundary, the storage architecture needs redesign; `setAccessLevel("TRUSTED_CONTEXTS")` does not distinguish the worker from other extension pages.
- If browser compatibility permits, restrict `storage.local` from content scripts as defense in depth, even though that half is random and useless alone.

### PKS-04 — Unzeroized temporary key copy

At `apps/extension/src/chrome/session/passkeyPersistence.ts:148`, `new Uint8Array(vaultKeyBytes)` creates an additional exact copy for encryption. The caller’s buffer is zeroized at `apps/extension/src/chrome/passkey/hydration.ts:137` and restored bytes are zeroized at `apps/extension/src/chrome/session/restoration.ts:216`, but this temporary copy is left to garbage collection.

This is not a practical independent exploit: a process-memory attacker can already inspect the live imported vault key and decrypted caches. It is nevertheless avoidable secret duplication.

#### Recommended remediation

- Pass the existing exact `Uint8Array` view directly as the WebCrypto `BufferSource`, or retain the temporary copy in a variable and zero it in `finally`.
- Add an offset-view unit case to ensure no oversized backing buffer is encrypted.

## 4. Proven security properties

The following invariants were verified:

- **Only the 32-byte general vault capability is persisted for passkey Never sessions.** Fresh passkey hydration passes only `vaultKeyBytes` and the factor binding at `apps/extension/src/chrome/passkey/hydration.ts:100`. No password, PRF output, mnemonic key, API key, private key, or phrase is included.

- **Cryptographic dimensions are exact.** The record requires a 32-byte plaintext, 12-byte IV, 16-byte GCM tag, 48-byte ciphertext, and 32-byte binding at `apps/extension/src/chrome/session/passkeyCredentialRecord.ts:7`. Unknown envelope fields are rejected.

- **Every write uses fresh randomness.** A new 32-byte AES key and 12-byte IV are generated at `apps/extension/src/chrome/session/passkeyPersistence.ts:128`.

- **AAD prevents meaningful swapping.** It binds the ciphertext to a versioned domain, exact session ID, literal `"master"` authority, and factor fingerprint at `apps/extension/src/chrome/session/passkeyPersistence.ts:34`.

- **The passkey fingerprint covers all current stable V1/V2 factor fields.** This includes RP ID, credential ID, salt, wrapped general key, V2 mnemonic wrapper/key ID, and creation time at `apps/extension/src/chrome/passkey/sessionBinding.ts:9`. Excluding `lastUsedAt` is safe because it is non-authoritative usage metadata and is updated after hydration.

- **Factor replacement is revalidated after decryption.** The current validated passkey record is reloaded and fingerprinted at `apps/extension/src/chrome/auth/walletUnlock.ts:53`.

- **Restoration is exactly Never-only and checks twice.** Authoritative sync storage is checked before decryption at `apps/extension/src/chrome/session/restoration.ts:81` and again after hydration at `apps/extension/src/chrome/session/restoration.ts:164`.

- **Persisted metadata cannot upgrade agent authority.** Passkey envelopes require persisted master metadata at `apps/extension/src/chrome/session/restoration.ts:138`, while the actual decrypted credential result remains authoritative at `apps/extension/src/chrome/session/restoration.ts:172`.

- **The restored credential cannot be forged through messages, JSON, spreading, or structured clone.** The brand symbol is module-local at `apps/extension/src/chrome/session/restoration.ts:26`; properties are non-enumerable at `apps/extension/src/chrome/session/restoration.ts:45`; ordinary non-string objects are rejected at `apps/extension/src/chrome/auth/walletUnlock.ts:41`. Reflection can expose it only to code already holding the live internal object.

- **Cold restoration deliberately excludes the V2 mnemonic key.** It hydrates with `{ password: null }` and no mnemonic capability at `apps/extension/src/chrome/auth/walletUnlock.ts:65`. V2 seed operations reject that state at `apps/extension/src/chrome/mnemonic/masterAccess.ts:90`.

- **Secret reveal still requires explicit master-password proof.** Both reveal paths pass through `verifyMasterPassword` and epoch revalidation at `apps/extension/src/chrome/secrets/revealHandlers.ts:36`.

- **Hydration is prepared before cache commit.** API and local vault decryption finish before the synchronous cache generation is published at `apps/extension/src/chrome/auth/sessionHydration.ts:220`. View-only wallets tolerate an absent API key and empty key vault.

- **Passkey removal revokes before factor deletion.** The local recovery key is removed before the passkey record at `apps/extension/src/chrome/passkey/removal.ts:67`.

- **Password rotation invalidates old passkey sessions even if later cleanup fails.** The master wrapper is rotated and passkey factor cleared in one local write at `apps/extension/src/chrome/auth/masterPasswordRotation.ts:184`.

- **Fallback browsers persist no secret-bearing recovery material.** The fallback branch clears existing secret halves and writes only non-restorable metadata at `apps/extension/src/chrome/session/passkeyPersistence.ts:116`.

### Storage-compromise consequences

| Attacker access | Result |
|---|---|
| Local storage only / copied closed profile | Random recovery key plus encrypted wallet records; no session ciphertext and no restored capability |
| Session storage only | Authenticated ciphertext with no AES recovery key |
| Both storage areas during the live browser session | General vault capability and routine signing authority; still no master password, PRF output, or V2 mnemonic key |
| Content script/page | Local half may be readable, but session ciphertext is unavailable by default |
| Trusted extension-page code execution | Both halves are accessible; this must be part of the documented trust boundary |

The split-capability approach is materially safer and simpler than persisting either the master password or PRF output.

  - session clear failure,

- Swap ciphertexts, local keys, session IDs, and passkey records between two simultaneous sessions/profiles.
- Explicit `lastUsedAt` mutation test proving it neither invalidates nor rescues a session.
- Persistence inspection including the master password, PRF output, V2 mnemonic key bytes, API key, private keys, and mnemonic—not only the current shorter secret list.
- A fresh module realm or subprocess test. Current “worker restart” tests mostly clear in-memory caches while module globals, startup promises, and transition state survive.

### Defense in depth

- Browser integration test proving content scripts cannot read session ciphertext.
- Browser-close/restart integration test for Chrome and Firefox.
- Frozen pre-change password Never-session fixture without the new discriminator, documenting whether one-time re-unlock is intended.
- Non-canonical base64, malformed pad bits, and 31/33-byte decrypted plaintext.
- Oversized ciphertext/binding/session metadata.
- V2 mutation of each stable fingerprint field independently.
- Extra passkey-record properties and reordered nested wrapper properties.
- Offset/backing-buffer cases for every typed-array crypto boundary.
- Native-upgrade cleanup where current ciphertext and local key are mismatched.
- Password-to-passkey and passkey-to-password torn transition cases.

The mock storage harness is useful: it structured-clones values and provides per-operation fault injection. It does not model `storage.onChanged`, real module unloading, browser session destruction, access levels, or worker termination between awaits.

### RE-01 — Low: simultaneous lock failure is not synchronized to other open wallet surfaces

#### Concrete path

When both recovery-half deletions fail, the background returns failure only
through the callback for the renderer that sent `lockWallet`:

- `apps/extension/src/chrome/background/authRouter.ts:268`
- `apps/extension/src/app/hooks/useManualWalletLock.ts:99`

That renderer clears its local secret-bearing state and enters the blocking
retry screen. Other already-open popup, sidepanel, or fullscreen surfaces
receive no failure event: the hook handles only `walletLockedExternal` and
`walletUnlockedExternal`, and the background emits no
`walletLockFailedExternal` event.

The new revocation test confirms both facts for simultaneous failure:

- no `walletLockedExternal` broadcast is sent; and
- both recovery halves remain usable by the restoration primitive.

Evidence: `apps/extension/tests/session/manualLockRevocation.test.ts:63`.

#### Failure conditions

1. At least two WalletChan extension surfaces are open.
2. Both the local recovery-key removal and session-half removal fail.
3. The user initiates manual lock from one surface.
4. Another surface subsequently queries or uses a path that restores an
   explicit Never session.

#### Impact

- The initiating surface correctly reports that lock could not be confirmed.
- Another open surface can remain visually unlocked and may trigger restoration
  of routine signing authority.
- The user is not silently shown success in the initiating surface, so this is
  materially less severe than the original PKS-01 behavior.
- The implementation does not satisfy the plural claim that trusted UI
  “surfaces remain in a blocking retry state” in
  `apps/extension/src/chrome/session/README.md:41`.

#### Recommended remediation

- Broadcast a background-to-renderer `walletLockFailedExternal` event when
  manual-lock teardown fails.
- Have every open App instance clear renderer secrets, suppress automatic
  biometric prompting, and enter the retry screen.
- Add a two-renderer test proving both surfaces enter the failure state.
- Optionally add a worker-local restoration barrier until a retry succeeds.
  Browser close remains the only absolute fallback when neither storage area
  accepts deletion.

## 9. Post-audit incident correction — fresh passkey account mutations

**Correction date:** 2026-07-17

The re-audit proved routine signing for Bankr, private-key, and seed-derived
accounts after a **cold** passkey Never-session restore. It did not prove
private-key or seed-phrase creation/import during the richer **fresh** V2
passkey session. Those are different authorization states, so the earlier
all-wallet signing result must not be read as all-passkey-flow coverage.

### Incident and root cause

A fresh V2 passkey session deliberately caches no plaintext master password,
but it does hold a coherent master type, general vault key, and live-only
mnemonic key. Several callers treated `getCachedPassword() === null` as a lost
session and invoked `tryRestoreSession()` even though that session was live.
The restoration primitive consumed the narrower persisted passkey envelope,
rehydrated only the general capability, rotated the auth epoch, and discarded
the mnemonic key.

- Private-key import captured its auth epoch before the redundant restore, so
  the later master-authority assertion rejected the mutation as
  “Authentication state changed.”
- Seed generation/import then lacked the V2 mnemonic key and failed with the
  biometric seed-protection recovery error.
- Routine transaction/signature paths continued to work because imported and
  seed-derived signing keys are recoverable through the general vault path.
- Bankr credential change also continued to work because it could encrypt with
  the restored general vault key and captured its epoch after restoration,
  although the redundant restore still silently removed mnemonic authority.

No plaintext disclosure or authority escalation was found; this was a
capability-downgrade and availability failure with critical product impact.

### Why the tests missed it

- `passkeyNeverSession.test.ts` covered cold-restored production signing, not
  fresh-passkey account mutation.
- `biometricSeedRouter.test.ts` covered passwordless V2 seed operations only
  with a finite timeout, so the Never-only redundant restore branch did not
  execute.
- `accountManagementRouter.test.ts` encoded the incorrect assumption that a
  missing password in Never mode should restore, and its fixture never modeled
  `{ password: null, live vault key: present }`.
- Router tests mocked restoration independently from the real auth epoch and
  mnemonic cache, hiding the cross-module state loss.
- The focused `test:passkey` command did not include the account-management,
  auth-router, restoration-policy, or biometric-seed router suites.

### Remediation and regression gates

- `tryRestoreSession()` is now idempotent for a coherent, expiry-checked live
  authorization generation after its authoritative timeout/manual-lock checks.
  It does not call unlock, rotate the epoch, or discard the mnemonic key.
- Private-key and Bankr mutations restore only when both password and general
  vault capability are absent. Private-key import captures its epoch after any
  necessary cold restore.
- Cached-password UI checks do not cold-restore an already-unlocked passkey
  session.
- Tests now reproduce the exact fresh V2 Never state and prove Bankr
  preparation, private-key import routing, seed import, auth-epoch stability,
  and mnemonic-key retention. The standard passkey gate includes those router
  and policy suites.
- Handler guidance and the security checklist now explicitly forbid using
  missing plaintext password as a passkey lock signal and require both fresh
  and cold Never-session coverage.

### Post-correction verification

- Focused auth/account/seed/restoration regression set: **43/43 passed**.
- Expanded `test:passkey`: **158/158 passed** across Bankr, private-key,
  seed-phrase, and reject-only impersonator behavior.
- Full `test:security`: the new passkey/auth cases passed; the run retained the

## 10. Follow-up hardening — mnemonic step-up and explicit agent-factor proof

The incident correction above preserves a rich fresh V2 passkey session, but a
deliberately narrower cold Never-session restore still cannot recover the
live-only mnemonic key. Seed import, generation, persistence, and derivation
therefore now use an explicit renderer step-up instead of surfacing a late
background error.

### Implemented behavior

- `getPasskeyUnlockStatus` separately reports whether the persisted V2 factor
  supports mnemonic recovery and whether its exact mnemonic key is live in the
  current worker session.
- Entering the seed setup/picker from a cold-restored V2 passkey session runs a
  fresh WebAuthn PRF assertion. The renderer proceeds only after a second
  status read proves that the matching mnemonic capability was hydrated.
- Seed generation, import continuation, final persistence, and derivation each
  recheck the gate so a worker restart while the screen is already open cannot
  silently bypass the step-up.
- Agent-password creation now collects the current master password explicitly.
  The service worker requires a live master session, decrypts the current
  master wrapper with that request value, and proves both general-vault and V2
  mnemonic recovery before publishing the agent wrapper. It never treats a
  passwordless passkey master session as implicit password confirmation.
- Passkey V1 remains readable for local development profiles but is
  intentionally blocked from new local-account setup. No released extension
  version emitted V1 records, so no production migration promise is implied.

### Test-gap correction

The prior tests independently covered cold routine signing and fresh V2 seed
handlers, but did not model the UI transition between the two capabilities.
The focused gate now covers the full matrix: fresh/cold passkey state, Bankr,
private-key and seed-phrase accounts, reject-only impersonators, explicit
master proof, one WebAuthn assertion, post-assertion mnemonic-capability
recheck, cancellation, stale/missing capability, and unreleased V1 behavior.

A follow-up search of every `getCachedPassword()` and session-restoration
caller found no second account-mutation path that still treats missing
plaintext password as proof that a live passkey session is locked. The
restoration primitive is also idempotent for a coherent live authorization,
which prevents routine signing/chat/batch callers from downgrading that
capability if they conservatively request restoration.
