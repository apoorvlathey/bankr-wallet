# WalletChan Extension — Security & Bug Review

**Date:** 2026-06-10
**Scope:** `apps/extension` (browser wallet extension). Focus on security edge cases and correctness bugs.
**Method:** Five parallel deep-review passes (crypto/session, dapp↔extension trust boundary, signing flows across all 4 wallet types, storage/migrations, confirmation-UI/display integrity) + a Semgrep static scan (`p/security-audit`, `p/secrets`, Trail of Bits, important-only). Every "High" finding below was independently re-verified against the source by reading the full code path.

---

## Executive summary

The extension is, on the whole, **well-architected for security**. The hard parts are done right: AES-256-GCM + PBKDF2 (600k) with fresh salt/IV everywhere, decryption-based unlock (no stored password hash), a non-extractable in-memory vault key, an account-pinning model that defeats confirm-time TOCTOU, comprehensive impersonator rejection across every signing path, `chainId === 0` EIP-7702 rejection, `eth_sign` rejected at intake, a central `EXTENSION_ONLY_MESSAGES` auth gate, sandboxed/escaped rendering of dapp-supplied content, and no page→background relay (`externally_connectable`/`onMessageExternal` absent). The Semgrep scan came back essentially clean (one false positive).

The review found **3 High**, **~10 Medium**, **~8 Low**, and several Info issues. None is a trivially-remote drain, but three are genuinely important:

| # | Severity | Title | Impact |
|---|----------|-------|--------|
| **C1** | High | Auto-lock never clears the cached vault key | "Locked" wallet can still decrypt/sign; documented timeout guarantee is violated |
| **U1** | High | SwapConfirmation infinite render loop | Swap confirmation popup crashes (blanks) on common swaps |
| **ST1** | High | Changing Bankr API-key+address never updates the account record | Address rotation silently ignored; dapps + signing use the old address |

The single recurring theme across Medium findings is **path divergence**: a hardening or feature lands on one surface (dapp-batch, the vault-key password-change branch, the guarded batch render path) but its sibling surface (cross-dapp batch, legacy password-change branch, swap render path) is missed. This is the project's own documented footgun, and it accounts for most of the real bugs here.

## HIGH

### C1 — Timed auto-lock never clears the cached vault key; signing bypasses the lock
**File:** `src/chrome/sessionCache.ts:210-219` (`getCachedVaultKey`), `:224-226` (`getPasswordType`); `src/chrome/crypto.ts:85-101` (`loadDecryptedApiKey`); PK/seed paths in `src/chrome/txHandlers.ts`.
**Status:** ✅ Fixed in `a94eea6` (`Enforce auto-lock for vault key cache`).
**Verified:** ✅ (read end-to-end)

Auto-lock is enforced *lazily*, inside the getters — there is **no `chrome.alarms` timer** that proactively wipes credentials (the only intervals keep the MV3 worker *alive*). The expiry checks live only in `getCachedApiKey` (`:111`), `getCachedPassword` (`:125`), and `getCachedVault` (`:181`). **`getCachedVaultKey()` and `getPasswordType()` have no timeout check at all** and return their cached value unconditionally.

The vault key is the master decryptor for every private key, mnemonic, and the Bankr API key. Because it is never expired on timeout:

- `loadDecryptedApiKey(password)` (`crypto.ts:90`) reads `getCachedVaultKey()` and decrypts `encryptedApiKeyVault` **ignoring the `password` argument entirely** — so after timeout, a confirm message with *any* password string signs successfully.
- The PK/seed fallbacks (`getPrivateKeyFromCache` → `decryptAllKeysWithVaultKey`) re-derive keys from the still-live vault key.

After timeout, `isWalletUnlocked()` returns false (the UI shows "locked", because it only consults the expiring getters) but the master key survives in service-worker memory indefinitely — until manual lock, a real `suspend`, or worker death. With a WalletConnect session keeping the worker warm, the documented "5 min / 1 hour" auto-lock provides far weaker protection than stated.

**Why High (with caveat):** This violates the documented auto-lock guarantee for the most sensitive artifact. Practical exploitation still requires reaching a sign/confirm handler, which are `EXTENSION_ONLY` (extension-context only) — so it is primarily a **defense-in-depth / documented-behavior failure** rather than a remote drain. Treat as High because it concerns the master key and the core lock invariant.

**Fix:** Make `getCachedVaultKey()` (and `getPasswordType()`) honor the same expiry as the other getters and null `cachedVaultKey`/`cachedPasswordType` when it fires; **or** add a `chrome.alarms`-based proactive lock that calls `clearAllAuthState()` on timeout. Gate all signing on a single `isUnlocked()` that also covers the vault key.

### U1 — `SwapConfirmation` `onFunctionName` triggers an infinite render loop (crashes the popup)
**File:** `src/components/Swap/SwapConfirmation.tsx:194-196` (handler), `:764` (call site); cf. `src/components/CalldataDecoder.tsx:225-229` (effect) and the **guarded** version in `src/components/BatchTransactionConfirmation.tsx:370-375`.
**Status:** ✅ Fixed in `e5194c8` (`Fix swap confirmation calldata labels`).
**Verified:** ✅ (read both surfaces)

`CalldataDecoder` fires its callback from an effect whose deps include the callback identity: `useEffect(… , [result?.functionName, onFunctionName])`. SwapConfirmation passes a **fresh inline arrow every render** (`onFunctionName={(name) => handleFunctionName(i, name)}`) and `handleFunctionName` **unconditionally returns a new object**:

```ts
const handleFunctionName = (index, name) =>
  setDecodedFunctionNames((prev) => ({ ...prev, [index]: name }));
```

Each render → new arrow → effect re-runs → `setState` returns a new reference → re-render → … React throws "Maximum update depth exceeded." `CalldataDecoder` being `memo`'d does not help — the changing prop identity defeats the memo. The batch surface defends against exactly this ("*Same value — skip update to avoid infinite loop*", returns `prev` when unchanged); the swap surface did not get the guard.

**Scenario:** A token→token swap that stages an `approve` call resolves `functionName = "approve"` → loop starts → popup crashes/blanks. (Dormant only when no inner call resolves a name.)

**Fix:** Mirror the batch surface — bail in `handleFunctionName` when `prev[index] === name`, and/or wrap it in `useCallback` with a stable per-index callback.

### ST1 — "Change API Key & Address" never updates `accounts[].address`
**File:** `src/components/AccountSettings.tsx:307-310`; no `updateAccountAddress` exists in `src/chrome/accountStorage.ts` (grep confirmed). Override at `src/chrome/inject.ts:224-242`.
**Status:** ✅ Fixed in `489c4e9` (`Fix Bankr address rotation`).
**Verified:** ✅ (grep + read)

The Bankr "change API key & address" flow saves the key via the correct handler but writes the address **only** to `chrome.storage.sync.{address, displayAddress}`. The multi-account source of truth — the `accounts[]` entry — is never updated (no updater function exists). All signing/pinning resolves the address from the account record (`txHandlers.ts:204` `getActiveAccount()`, `:216-227` rejects `from` mismatches), and `inject.ts:230` explicitly **flips `store.address` back** to `account.address` and emits `accountsChanged`.

**Scenario:** A Bankr user rotates their wallet (new address + key) → success toast → every subsequent dapp interaction and tx still uses the **old** address (and the dapp's `accountsChanged` state flip-flops). Effectively a broken/foot-gun feature.

**Fix:** Add `updateAccountAddress(accountId, address)` to `accountStorage.ts`, call it in the save flow (and broadcast `accountsUpdated`), or remove the address field from this form.

## MEDIUM

### M1 / S4 — Privileged handlers missing from `EXTENSION_ONLY_MESSAGES` (incl. `submitChatPrompt`)
**File:** `src/chrome/background.ts:694-782` (the set); handlers at `:3052` (`submitChatPrompt`), `:1418` (`getAccounts`), `:1462` (`setTabAccount`), `:2541` (`initiateTransfer`), `:1255` (`splitBatchIntoIndividualTxs`), `:2884` (`cancelProcessingTx`), chat CRUD `:3063-3108`, plus read/probe handlers.
**Status:** ✅ Fixed in `39c58fa` (`Gate UI-only background messages`).
**Verified:** ✅ (the three headline handlers confirmed absent from the set; `setTabAccount` confirmed to trust `message.tabId`). *Independently flagged by two separate review passes.*

The central auth gate only rejects content-script senders for types in `EXTENSION_ONLY_MESSAGES`. The handlers above are neither in the set nor have an internal `isExtensionPage(sender)` check. The standout is **`submitChatPrompt`**, which spends the cached API key to drive the Bankr **agent** (an execution surface) with a free-text prompt and **no confirmation popup anywhere** — the chat path bypasses the entire pending-tx flow. `getAccounts`/`getTxHistory`/`getChatConversations` leak the full account list and history; `setTabAccount` accepts an **arbitrary** `message.tabId` (cross-tab write).

**Reachability:** Not page-reachable *today* — `inject.ts` forwards only a fixed `i_*` message vocabulary. This is the exact "could a compromised content-script context abuse this?" layer the gate is meant to be, so it should not depend on `inject.ts` staying narrow.

**Fix:** Add all read/mutation/probe/chat handlers to `EXTENSION_ONLY_MESSAGES` (keep the dapp-facing `i_*` + `getActiveAccount` reachable). For `setTabAccount`, bind to `sender.tab?.id` only.

### M3 — No connection/permission model; every site silently learns the active address
**File:** `src/chrome/impersonator.ts:195-202`.

`eth_requestAccounts` returns `[this.address]` with no approval prompt and `eth_accounts` returns it unconditionally, on every page. Any visited site can read the active wallet address on load with zero interaction — a cross-web fingerprinting / targeted-phishing enabler, divergent from the EIP-1193 norm (`[]` until approved). May be intentional given the "Impersonator" lineage, but the product now custodies real keys.
**Fix:** Per-origin connection permission: `eth_accounts` → `[]` for un-approved origins; `eth_requestAccounts` opens an approval popup keyed on `sender.origin` and persists the grant.

### S1 — Cross-dapp 7702 ship path omits the EIP-7702 authorization gas bump
**File:** `src/chrome/crossDappBatchHandlers.ts:1061-1117` (`shipCrossDappBatchPkSp`); cf. `batchTxHandlers.ts:1760` and `txHandlers.ts:1237` which both bump.
**Status:** ✅ Fixed in `1692bc1` (`Fix cross-dapp 7702 gas bump`).
**Verified:** ✅ (confirmed `bumpGasForEip7702Auth` is never imported/called in this file)

When a cross-dapp PK/SP batch needs the first delegation (`needsAuthorization`), it signs an `eip7702` tx (`:1114`) but sets gas to `summedFromEstimates`/`fallbackGas` with **no** `bumpGasForEip7702Auth`. The auth tuple's intrinsic cost (150k/300k floors on MegaETH per the project's own constants) is invisible to the state-override simulation → the first cross-dapp batch on a not-yet-delegated chain is systematically under-gassed ("intrinsic gas too low" / OOG revert). The dapp-batch and single-tx paths work because they bump.
**Fix:** Apply `bumpGasForEip7702Auth(chainId, BigInt(gasHex), 1)` when `needsAuthorization`, mirroring `processBatchTransactionAtomic7702InBackground`.

### S2 — Non-atomic batch: stranded higher-nonce txs can execute long after the bundle "failed"
**File:** `src/chrome/batchTxHandlers.ts:1169-1231`; same pattern in `txHandlers.ts:2101-2192` (swap PK phase 2).
**Status:** ✅ Fixed in `f322ad1` (`Order local multi-tx broadcasts`).

Nonces are pre-assigned sequentially, then all calls are signed and broadcast **concurrently** (`Promise.all`). If call *i* fails at broadcast but calls *i+1…n* were accepted into the mempool, `resetNonce` clears the cache but the broadcast tail stays valid. The next tx the user sends fills the gap and the **stale tail executes later** — possibly a swap without its approve, hours after the user believed the bundle failed.
**Fix:** Broadcast strictly sequentially and stop on first failure; or broadcast gap-filler replacements for orphaned nonces; at minimum surface "N calls may still execute later" in the failure notice.

### U2 — No error boundary + unsanitized `tx.value` → malformed value blanks the popup
**File:** `src/components/TransactionConfirmation.tsx:610-617` & `:879-891` (`BigInt(value)` at render); intake `txHandlers.ts:239-252` (no value validation); no `ErrorBoundary` anywhere (`App.tsx` uses only `<Suspense>`).
**Status:** ✅ Fixed in this change. Injected and WalletConnect transaction intake now validate/normalize `tx.value` before persistence; legacy malformed pending requests render a warning with signing blocked, and the single-tx confirmation is wrapped in a reject-capable error boundary.

`tx.value` flows untouched from the dapp into render. `isValueZero` only special-cases `"0"`/`"0x"`/`"0x0"`; any other non-numeric string (`"abc"`, `"0x1.5"`, `"1e30"`) reaches `BigInt(value)` and throws. With no error boundary the popup tree unmounts and **goes blank**; the request lingers 30 min and reopening re-crashes — the user has no in-popup way to Reject. Availability/UX, no funds at risk. (The batch surface is safe — it wraps the sum in try/catch.)
**Fix:** Validate/normalize `value` at intake; wrap confirmation views in an error boundary that still renders Reject / Reject-All.

### U3 — Swap per-call Value row hardcodes "ETH" regardless of native symbol
**File:** `src/components/Swap/SwapConfirmation.tsx:123-127` (`formatValue`), used `:746`.
**Status:** ✅ Fixed in this change. Swap per-call and bridge-fee native value labels now resolve the source chain's native symbol from `networksInfo`, falling back to built-in chain config/ETH only if runtime metadata is unavailable.

The expandable per-tx Value row always prints `"… ETH"`. A native-in swap on BNB Chain/Polygon (selling BNB/POL, so `msg.value > 0`) shows "0.5 ETH" instead of "0.5 BNB" — a misleading native-asset label on what the user is signing. The Bridge Fee row and batch surface already resolve the symbol correctly.
**Fix:** Resolve via `getNativeAssetMeta(chainId, networksInfo)` per the project guardrail and thread it into `formatValue`.

### ST2 — Legacy-system password change is non-atomic and never re-encrypts `mnemonicVault`
**File:** `src/chrome/authHandlers.ts:632-657`.
**Status:** ✅ Fixed in this change. The no-vault-key legacy password-change path now computes new `encryptedApiKey`, `pkVault`, and `mnemonicVault` values in memory and persists them in one `chrome.storage.local.set()` call.

The vault-key branch was hardened (single atomic write, round-trip verify, mnemonic re-encryption). The legacy branch was not: `saveEncryptedApiKey` and `reEncryptVault` are separate writes (SW death between them → permanently broken PK/seed signing and un-completable migration), and `reEncryptMnemonicVault` is **never called** (a legacy-mode user with mnemonics loses seed access after a password change). Low likelihood (requires legacy system still active) but key-loss impact.
**Fix:** Mirror the vault-branch pattern — compute all re-encryptions in memory, then one `chrome.storage.local.set`.

### ST3 — Read-modify-write races on pending-request stores (requests silently dropped)
**File:** `src/chrome/pendingTxStorage.ts:82-99`, `pendingSignatureStorage.ts`, `pendingBatchTxStorage.ts`, `pendingWatchAssetStorage.ts`, `pendingAddChainStorage.ts`, `walletConnectStorage.ts:35-74`, `accountStorage.ts:125-143`, `customTokenStorage.ts:30-43`.
**Status:** ✅ Fixed in `9d9d3ae` (`Fix pending storage write races`).

The team already ships a write mutex on `txHistoryStorage.ts`/`bundleStatusStorage.ts`/`pendingBridgeStorage.ts` (with a comment describing a production clobber). The pending-request stores — which have *more* concurrent writers, including the per-minute `clearExpiredTxRequests` cleanup interval — have **no lock**. A request saved between the cleaner's read and write is erased → the dapp's promise hangs and the confirmation never appears.
**Fix:** Extract the `withLock` helper into a shared module; wrap every RMW on these keys.

### ST4 — `networksInfo`: popup writes back a stale full snapshot; no `onChanged` subscription
**File:** `src/contexts/NetworksContext.tsx:30-62`; `src/chrome/background.ts:1025-1090`.
**Status:** ✅ Fixed in `820b494` (`Fix network settings storage races`).

`NetworksContext` reads `networksInfo` once on mount and rewrites the entire object on change; no component listens for `changes.networksInfo`; the background also writes it in `confirmAddChain` (dual writers). A long-lived sidepanel + a dapp-initiated chain add → later toggling a chain's hidden flag writes the stale snapshot back and **deletes the newly-added chain**; if `chainName` pointed at it, the `inject.ts:197-202` guard fails and providers stop initializing.
**Fix:** Subscribe to `chrome.storage.onChanged` for `networksInfo` and merge, or route all writes through one background handler.

### ST5 — Failed seed import orphans a `seedGroups` entry + an encrypted mnemonic copy
**File:** `src/chrome/background.ts:1766-1817` (`addSeedPhraseGroup`).
**Status:** ✅ Fixed in `f2d5cb5` (`Fix duplicate seed import storage leak`).

`addSeedGroup` (writes `seedGroups`) and `storeMnemonic` (writes `mnemonicVault`) run **before** the per-index duplicate checks. When all indices collide (`importedAccounts.length === 0`), the user is told "All selected addresses already exist" — but the group and **the encrypted seed phrase persist in storage with no account referencing them**, never cleaned (cleanup only triggers on last-account removal of a group). Security-relevant: the user believes the import failed, yet a copy of their seed lives encrypted in `chrome.storage.local` until a full reset.
**Fix:** Validate collisions before writing anything, or roll back (`removeSeedGroup` + `removeMnemonic`) on the zero-imported / thrown-error paths.

### ST6 — `resetExtension` leaves wallet-coupled state behind
**File:** `src/chrome/background.ts:2990-3033`; `txHandlers.ts:1826-1832`.
**Status:** ✅ Fixed in this change (`Fix extension reset cleanup`).

The remove list omits `crossDappBatch` (staged txs whose count badge will then count for the *new* wallet), `pendingBatchTxRequests`, `pendingWatchAssetRequests`, `pendingAddChainRequests`, `walletConnectPendingRequests`, `walletConnectChainId`, `pendingBridges`, `bundleStatuses`, `customTokens`, `recentlyReceivedTokens`, and the `addChainResult:`/`watchAssetResult:`/`batchTxResult:`/`batchTxAck:`/`capabilitiesResult:`/`callsStatusResult:` prefixes (only `txResult:`/`sigResult:` are swept). After "reset", the old wallet's staged batch, bridge history, and WC bridges survive into the new identity.
**Fix:** Maintain a single `ALL_WALLET_KEYS` constant (assert against STORAGE.md in a test) and reset from it; sweep all `*Result:`/ack prefixes.

### ST7 — Firefox `storage.session` shim stores both halves of the session password on disk
**File:** `src/chrome/sessionStorage.ts:55-64`; `sessionCache.ts:273-301, 497-525`.
**Status:** ❌ Invalid/stale for supported Firefox. WalletChan's Firefox manifest requires Firefox `121.0+`, while native in-memory `storage.session` shipped in Firefox 115; the local-storage shim path is not used on the supported AMO target.

The split-storage design ("compromising either area alone does not reveal the password") collapses on Firefox: `encryptedSessionPassword` is shimmed into `chrome.storage.local` (`__session__` prefix) and `sessionEncKey` is *already* in `storage.local`. With auto-lock "Never" (the default), the **master password is recoverable from the profile directory while the browser is closed** — strictly weaker than Chrome (where the ciphertext half is memory-only). The `onStartup` wipe only runs on next launch; after a crash + disk image, both halves are present. The in-code comment claims parity that holds only for a *running* browser.
**Fix:** On Firefox, derive the wrapping key from something not co-located, or refuse to persist the session password on the shim path (require re-unlock after restart); document the trade-off in FIREFOX.md.

### ST8 — Quota risk: no `unlimitedStorage`, 5 MB image cache, several never-pruned key families
**File:** `public/manifest.json:56-63`; `avatarImageCache.ts:16-18`; `swapApi.ts`; `lib/ethShLabelsCache.ts`; `coingeckoService.ts`.
**Status:** ✅ Fixed in this change. Added `unlimitedStorage` to both extension manifests, made non-critical cache writes best-effort, and added service-worker startup/6-hour pruning for expired metadata/image cache entries.

`chrome.storage.local` is capped at 10 MB without `unlimitedStorage`. The avatar cache alone is 5 MB. `tokenInfo:`/`tokenLogo:`/`ethShLabels:`/`cs:desc:` and coingecko caches honor TTLs **only on read** — expired entries are never deleted and grow one key per contract ever rendered. When quota is hit, **all** `chrome.storage.local.set` calls throw — including `savePendingTxRequest`, `saveVault` (account import), and result writes — so wallet-critical writes fail because of cache bloat.
**Fix:** Add `unlimitedStorage`, or a periodic sweep deleting expired cache keys.

## What was verified sound (selected)

- **Crypto primitives:** AES-256-GCM + PBKDF2-SHA256 @ 600k, 16-byte salt + 12-byte IV, **fresh per encryption** via `crypto.getRandomValues` — no IV/salt reuse, no `Math.random`, no `eval`. Vault key is a non-extractable in-memory `CryptoKey`. Unlock is **decryption-based** (no stored password hash to bypass). Agent-password set is rejected if it equals/decrypts the master wrapper.
- **Agent-password access control:** signing works for all signing types incl. agent; private-key/seed **reveal is blocked for agent regardless of wallet type** (verified each reveal path); `resolvePasswordType` closes the post-restart null-bypass.
- **Suspend/lock:** `suspend`, manual `lockWallet`, password-change, and `resetExtension` all fully wipe in-memory + session storage (the C1 gap is specifically the *timed* path).
- **Trust boundary:** `externally_connectable`/`onMessageExternal` absent; `e.source === window` enforced on both bridge ends; all request IDs `crypto.randomUUID()`; RPC proxy rejects non-configured URLs and attaches no credentials; dapp-supplied favicon/origin sanitized; no `dangerouslySetInnerHTML` in the dapp-facing path; asset-change HTML rendered in a `sandbox=""` iframe with escaping + image-URL allowlist.
- **Signing correctness:** impersonator rejected at type-level **and** runtime across every execution path (tx, batch, cross-dapp, swap, sponsored transfer, SIWE, WalletConnect, split-mode); account **pinning** defeats confirm-time account switch; `from`/signer re-checked against the pinned account at sign time (all `toLowerCase()` — no case bugs); gas overrides applied at sign time with legacy `gasPrice` cleared; `chainId === 0` 7702 auth rejected; 7702 race re-checks onchain delegate before broadcast; custom delegates are UI-cache only (a dapp cannot set/upgrade the delegate); ERC-7821 self-recursion guarded; `wallet_getCapabilities` address-scoped.
- **Confirmation UI:** gas-feature parity (isNonAtomic / onGasEstimates / onValidityChange / sign-time overrides) wired on all four surfaces; approval-mismatch race prevented (pinned id + same-id refresh guard); double-submit guarded (UI + `processingTxIds`); unlimited-approval shown with a red chip and `BigInt` math; simulation failure shows an "unavailable" banner (does **not** fake-safe); Reject-All uses `chart.negative`; copy uses icon-toggle, never toasts.
