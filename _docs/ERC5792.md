# ERC-5792 Batch Transaction Support

## Overview

ERC-5792 enables dapps to submit multiple calls as a single atomic batch transaction. WalletChan supports this for **Bankr API accounts** (smart accounts) on **Bankr-compatible chains**, encoding batches via ERC-7821's `execute(mode, executionData)` function.

**Spec**: https://eips.ethereum.org/EIPS/eip-5792

**Related files**:

| File | Purpose |
|---|---|
| `chrome/erc5792Types.ts` | Type definitions, status codes, error codes |
| `chrome/batchTxHandlers.ts` | Core handler logic + ERC-7821 encoding |
| `chrome/pendingBatchTxStorage.ts` | Pending batch request persistence |
| `chrome/bundleStatusStorage.ts` | Bundle status tracking for `getCallsStatus` |
| `chrome/txSimulation.ts` | `simulateBatchAssetChanges()` — batch asset change simulation |
| `components/BatchTransactionConfirmation.tsx` | Batch confirmation UI |
| `contracts/src/utils/TxSimulator.sol` | `simulateBatch()` — on-chain sequential batch simulator |

## JSON-RPC Methods

### `wallet_getCapabilities(address, chainIds?)`

Returns per-chain capabilities. For eligible accounts (Bankr/impersonator type) on Bankr-supported chains, returns:

```json
{
  "0x2105": { "atomic": { "status": "supported" } },
  "0x1": { "atomic": { "status": "supported" } }
}
```

For non-Bankr account types (privateKey, seedPhrase), returns `"unsupported"`.

### `wallet_sendCalls({ version, chainId, calls, atomicRequired?, from?, id? })`

Receives a batch of calls and opens the confirmation popup. Returns `{ id }` immediately (the bundle ID). The dapp then polls `wallet_getCallsStatus` for the result.

**Validations performed:**
- `version` must be `"2.0.0"`
- `chainId` must be a Bankr-supported chain
- Active account must be `bankr` or `impersonator` type
- `from` (if provided) must match the active account address

### `wallet_getCallsStatus(bundleId)`

Returns the bundle lifecycle status:

| Status | Meaning |
|---|---|
| `100` | Pending — awaiting user confirmation or tx not yet on-chain |
| `200` | Confirmed — tx included on-chain successfully |
| `400` | Offchain failure — user rejected, request expired, or submission error |
| `500` | Reverted — tx included on-chain but reverted |

Response includes `receipts` array (with logs, gasUsed, txHash) when the tx is confirmed.

### `wallet_showCallsStatus(bundleId)`

Opens the block explorer for the bundle's transaction hash (if available).

## Message Flow

### wallet_sendCalls (full lifecycle)

```
1. Dapp calls provider.request({ method: "wallet_sendCalls", params: [...] })

2. impersonator.ts (inpage)
   - Creates request UUID, sends i_walletSendCalls via window.postMessage
   - Waits for walletSendCallsResult

3. inject.ts (content script)
   - Generates bundleId (UUID — never dapp-controlled)
   - Starts waitForStorageResult("batchTxAck:{bundleId}")
   - Fires chrome.runtime.sendMessage({ type: "walletSendCalls", bundleId, params, origin, favicon })

4. background.ts (service worker)
   - Routes to handleWalletSendCalls() in batchTxHandlers.ts

5. batchTxHandlers.ts
   - Validates params (version, chainId, account type, from address)
   - Saves PendingBatchTxRequest to pendingBatchTxStorage
   - Creates initial BundleStatus (status: 100) in bundleStatusStorage
   - Writes ack to chrome.storage.local("batchTxAck:{bundleId}")
   - Opens popup via openExtensionPopup()

6. inject.ts picks up ack → posts walletSendCallsResult to impersonator.ts
7. impersonator.ts resolves with { id: bundleId }
8. Dapp receives the bundle ID, can now poll wallet_getCallsStatus

9. Popup renders BatchTransactionConfirmation.tsx
   - Shows collapsible call cards with decoded function names
   - Shows asset changes for the combined batch (via encoded ERC-7821 tx)
   - Shows Tenderly simulation link

10. User clicks Confirm
    - Sends confirmBatchTransactionAsync message to background
    - batchTxHandlers.ts: encodes calls via ERC-7821, submits to Bankr API
    - Updates BundleStatus (200/400/500), writes batchTxResult, shows notification
    - Saves to txHistory with "Batch: func1, func2" as function name

11. User clicks Reject
    - Updates BundleStatus to 400 ("User rejected")
    - Writes rejection to batchTxResult storage
```

### wallet_getCallsStatus

```
Dapp → impersonator.ts → inject.ts → background.ts → bundleStatusStorage.get() → response
```

### wallet_getCapabilities

```
Dapp → impersonator.ts → inject.ts → background.ts → check account type + chain → response
```

## ERC-7821 Batch Encoding

Bankr wallet addresses are smart accounts that support ERC-7821 batch execution. Multiple calls are encoded into a single transaction:

```
to:    walletAddress (calls itself)
value: sum of all call values
data:  execute(BATCH_MODE, encodedCalls)
```

**Encoding logic** (in `batchTxHandlers.ts → encodeBatchCalls()`):

```typescript
const ERC7821_ABI = [{
  name: "execute",
  inputs: [
    { name: "mode", type: "bytes32" },
    { name: "executionData", type: "bytes" },
  ],
  stateMutability: "payable",
  type: "function",
}];

const ERC7821_BATCH_MODE =
  "0x0100000000007821000100000000000000000000000000000000000000000000";

// 1. Encode calls as tuple[] → (address to, uint256 value, bytes data)[]
const executionData = encodeAbiParameters(
  [{ type: "tuple[]", components: [
    { type: "address", name: "to" },
    { type: "uint256", name: "value" },
    { type: "bytes", name: "data" },
  ]}],
  [calls],
);

// 2. Encode the execute function call
const calldata = encodeFunctionData({
  abi: ERC7821_ABI,
  functionName: "execute",
  args: [ERC7821_BATCH_MODE, executionData],
});
```

This same encoding pattern is used in the website admin page (`AdminContent.tsx`) for the Clanker Fee batch claim.

## Simulation & Tenderly

### Asset Change Simulation

Batch transactions are **self-calls** (`from === to = wallet address`) for ERC-7821 execution. This breaks the normal simulation approach because the state override replaces the wallet's code with the simulator bytecode, making the self-call hit the simulator instead of the smart account.

**Solution**: `TxSimulator.sol` has a dedicated `simulateBatch()` function that executes all calls **sequentially within a single `eth_call`**. This preserves state between calls (e.g., an `approve` in call 1 persists for the `swap` in call 2).

```
BatchTransactionConfirmation passes batchCalls[] to AssetChangesDisplay
  → AssetChangesDisplay sends "simulateBatchAssetChanges" message
    → background calls simulateBatchAssetChanges() in txSimulation.ts
      → createAccessList per call (parallel) → merge candidate addresses
      → encodeFunctionData(simulateBatch, [calls, candidates])
      → eth_call with state override: simulator bytecode at wallet address
      → Simulator executes all calls sequentially, snapshots balances before/after
      → Returns cumulative (ethDelta, tokens[], deltas[])
      → enrichTokenChanges() for metadata + prices
```

**Why this works**: The simulator is deployed at the wallet address, so `msg.sender` for each call is the wallet address (approvals go to the right place), and `address(this)` gives real `balanceOf` results.

**Key constraint**: When updating `TxSimulator.sol`, you must recompile (`forge build`) and copy the **exact** `deployedBytecode.object` from `out/TxSimulator.sol/TxSimulator.json` into `SIMULATOR_BYTECODE` in `txSimulation.ts`. A bytecode mismatch (even from a different compilation run) causes `InvalidJump` EVM errors because jump offsets differ.

### Tenderly

Tenderly still uses the **encoded ERC-7821 batch calldata** (the actual on-chain transaction format). The `BatchTransactionConfirmation` component constructs a synthetic `PendingTxRequest` with:

- `to` = wallet address (self-call)
- `data` = ERC-7821 encoded batch
- `value` = sum of all call values

This synthetic request is used to build the Tenderly simulation URL.

## Error Codes (ERC-5792)

| Code | Name | When |
|---|---|---|
| `4001` | User Rejected | User clicks Reject |
| `4100` | Unauthorized | `from` doesn't match active account |
| `5700` | Unsupported Capability | Required capability not supported |
| `5710` | Unsupported Chain | Chain not in `BANKR_SUPPORTED_CHAIN_IDS` |
| `5720` | Duplicate ID | Bundle ID already exists |
| `5730` | Unknown Bundle ID | `getCallsStatus` with unknown ID |
| `5760` | Atomic Not Supported | Active account doesn't support batching |

## Future: EIP-7702 for PK/Seed Phrase Accounts

EIP-7702 allows EOA accounts to temporarily delegate to a smart contract implementation for a single transaction. This enables batch execution for private key and seed phrase accounts without permanently converting them to smart accounts.

### How It Works

EIP-7702 introduces a new transaction type that includes an `authorizationList` — a signed authorization from the EOA to delegate its code to a specific contract address for the duration of the transaction. The EOA temporarily "becomes" a smart account, executes the batch, and reverts to a normal EOA afterward.

### Implementation Plan

#### 1. Extend `wallet_getCapabilities`

In `batchTxHandlers.ts → handleWalletGetCapabilities()`:

```typescript
// Current: only Bankr accounts return "supported"
// Future: also return "supported" for PK/seed accounts on 7702-compatible chains

const is7702Supported = EIP7702_CHAIN_IDS.has(chainId);
const isBankrAccount = account?.type === "bankr" || account?.type === "impersonator";
const isPKAccount = account?.type === "privateKey" || account?.type === "seedPhrase";

capabilities[hexChainId] = {
  atomic: {
    status: isBankrAccount
      ? "supported"
      : (isPKAccount && is7702Supported)
        ? "supported"
        : "unsupported",
  },
};
```

Add a new `EIP7702_CHAIN_IDS` set in `chainRegistry.ts` (or a `isEip7702Supported` flag per chain entry).

#### 2. Add `handleConfirmBatchTransactionPK()` in `batchTxHandlers.ts`

New handler following the same pattern as `handleConfirmTransactionAsyncPK()` in `txHandlers.ts`:

- Get private key from vault cache (same credential retrieval pattern)
- Encode calls via ERC-7821 (same `encodeBatchCalls()` function — encoding is account-type-agnostic)
- Construct an EIP-7702 transaction:
  ```typescript
  {
    type: "eip7702",  // New tx type
    to: accountAddress,
    data: encodedBatchCalldata,
    value: totalValue,
    authorizationList: [{
      chainId,
      address: ERC7821_IMPLEMENTATION,  // The contract to delegate to
      nonce: accountNonce,
      // Signed by the EOA's private key
    }],
  }
  ```
- Sign and broadcast via `signAndBroadcastTransaction()` from `localSigner.ts` (needs extension for 7702 tx type)
- Update bundle status and tx history (same as Bankr path)

#### 3. Add background router case

```typescript
case "confirmBatchTransactionAsyncPK": {
  const tabId = message.tabId || sender.tab?.id;
  handleConfirmBatchTransactionPK(
    message.bundleId,
    message.password,
    tabId,
    message.functionNames,
    message.gasOverrides,
  ).then((result) => sendResponse(result));
  return true;
}
```

#### 4. Update `BatchTransactionConfirmation.tsx`

The UI component already receives `accountType` and can branch the confirm handler:

```typescript
const messageType =
  accountType === "privateKey" || accountType === "seedPhrase"
    ? "confirmBatchTransactionAsyncPK"
    : "confirmBatchTransactionAsync";
```

#### 5. Update `localSigner.ts`

Add support for constructing and signing EIP-7702 transactions. The viem library already supports this via `signAuthorization()` and the `eip7702` transaction type.

#### 6. Chain Registry Update

Add `isEip7702Supported: boolean` to `ChainEntry` in `chainRegistry.ts`. This flag tracks which chains have deployed EIP-7702 support. Derive `EIP7702_CHAIN_IDS` set from it.

### Key Principle

The ERC-7821 encoding is **identical** for both paths — the only difference is how the encoded transaction gets submitted:

| | Bankr API Account | PK/Seed Account (7702) |
|---|---|---|
| Encoding | `encodeBatchCalls()` | `encodeBatchCalls()` (same) |
| Tx type | Standard tx via Bankr API | EIP-7702 tx with authorization |
| Signing | Bankr API signs | Local private key signs |
| Broadcast | Bankr API broadcasts | Local RPC broadcast |
| Smart account | Permanent (Bankr wallet is a smart account) | Temporary (7702 delegation for one tx) |
