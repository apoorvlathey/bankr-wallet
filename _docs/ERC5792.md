# ERC-5792 Batch Transaction Support

## Overview

ERC-5792 enables dapps to submit multiple calls as a batch transaction. WalletChan supports this for **all account types**:

| Account Type | Batching Mode | Strategy |
|---|---|---|
| `bankr` / `impersonator` | **Atomic** | ERC-7821 encoding → single tx via Bankr API |
| `privateKey` / `seedPhrase` | **Auto-Sequential** | Sequential nonces → individual txs broadcast concurrently |

Auto-sequential batching reduces wallet popups (single confirmation for N calls) and assigns sequential nonces automatically, providing a much better UX than N individual tx confirmations. In the future, EIP-7702 will enable atomic batching for EOA accounts as well.

**Spec**: https://eips.ethereum.org/EIPS/eip-5792

## JSON-RPC Methods

### `wallet_getCapabilities(address, chainIds?)`

Returns per-chain capabilities for chains where WalletChan can actually provide the advertised behavior:

**Bankr accounts** — on `BANKR_SUPPORTED_CHAIN_IDS`:
```json
{ "0x2105": { "atomic": { "status": "supported" } } }
```

**Impersonator accounts** advertise on standard chains so dapps surface the inspect-only batch UI; confirmation remains disabled because impersonators cannot sign.

**PK/SP accounts** — on built-in Pectra chains, added `KNOWN_CHAINS` custom chains, or any chain where `resolveActiveDelegate()` finds a usable onchain EIP-7702 path:
```json
{ "0x2105": { "atomic": { "status": "supported" } } }
```

**Why this is resolver-gated for EOAs**: PK/SP accounts now execute multi-call batches atomically via EIP-7702 + ERC-7821 when the resolver can use an onchain delegate or authorize WalletChan's default delegate. If the EOA is already delegated to an incompatible contract, capability is omitted so dapps don't send `atomicRequired` batches that cannot ship.

**MegaETH / non-standard gas**: PK/SP atomic 7702 is advertised on MegaETH when the resolver qualifies the account. The UI estimates the single wrapped ERC-7821 tx and the signer uses that exact estimate. The old auto-sequential capability path still excludes non-standard-gas chains because dependent per-call gas remains unreliable there.

### `wallet_sendCalls({ version, chainId, calls, atomicRequired?, from?, id? })`

Receives a batch of calls and opens the confirmation popup. Returns `{ id }` immediately (the bundle ID). The dapp then polls `wallet_getCallsStatus` for the result.

**Validations performed:**
- `version` must be `"2.0.0"`
- `chainId` must be supported (Bankr chains for Bankr accounts, all `ALLOWED_CHAIN_IDS` for PK/SP)
- Active account must be `bankr`, `impersonator`, `privateKey`, or `seedPhrase`
- `from` (if provided) must match the active account address
- `atomicRequired` is ignored for PK/SP accounts (always executes non-atomically)

### `wallet_getCallsStatus(bundleId)`

Returns the bundle lifecycle status:

| Status | Meaning |
|---|---|
| `100` | Pending — awaiting user confirmation or tx not yet onchain |
| `200` | Confirmed — tx included onchain successfully |
| `400` | Offchain failure — user rejected, request expired, or submission error |
| `500` | Reverted — tx included onchain but reverted |
| `600` | Partial revert — some txs succeeded, some reverted (non-atomic only) |

Response includes `receipts` array (with logs, gasUsed, txHash) when confirmed. For non-atomic batches, there is one receipt per call, **reversed** (last call's receipt first) so dapps that use `receipts.find()` pick the meaningful tx (e.g., swap, not approve). The `atomic` field is `false` for non-atomic bundles. The `txHash` field on `BundleStatus` is set to the **last successful tx** (e.g., the swap, not the approve) — this is what dapps typically show to users.

### `wallet_showCallsStatus(bundleId)`

Opens the block explorer for the bundle's primary transaction hash (last successful tx).

## Split mode (escape hatch for non-standard custom chains)

The wallet's `wallet_getCapabilities` already filters known chains with non-standard gas models (e.g. MegaETH) so well-behaved dapps fall back to single-tx `eth_sendTransaction` on those. But for *unknown* custom chains the user manually adds that behave the same way (dual gas models, broken `eth_simulateV1`, GAS-opcode-blind simulators), the wallet still advertises batch capability and the dapp keeps sending `wallet_sendCalls`. In that case the dependent-call gas estimate falls back to a generous default, the swap OOG-reverts, and the user is stuck.

Split mode is the in-popup escape hatch:

1. The batch confirmation popup (`BatchTransactionConfirmation.tsx`) shows a gear `IconButton` to the right of the `CALLS` header. Visible only for `accountType === "privateKey" | "seedPhrase"` (Bankr atomic and impersonator read-only are exempt — they don't have the underlying problem). `params.atomicRequired` is intentionally NOT checked: PK/SP auto-sequential broadcast already ignores it, so the bundle is effectively non-atomic regardless of what the dapp requested — split is just another non-atomic execution path.
2. Clicking the gear opens a Chakra modal explaining what split does. The user confirms.
3. The frontend sends `splitBatchIntoIndividualTxs` to the background. `handleSplitBatchIntoIndividualTxs` in `chrome/splitBatchSequencer.ts`:
   - Validates eligibility (account type, `atomicRequired`).
   - Snapshots trusted context (account, origin, tab/window, favicon, chainName) onto the existing `BundleStatus` via a new `splitContext` field — needed because the `PendingBatchTxRequest` is removed once split mode starts.
   - Sets `splitMode: true`, `splitCalls: params.calls`, `splitNextIndex: 0`, `atomic: false` on the bundle.
   - Acks `batchTxResult:{bundleId}` so the batch popup closes through the existing channel.
   - Calls `enqueueNextSplitCall(bundleId)`, which builds a `PendingTxRequest` for `splitCalls[0]` (txId `${bundleId}:split:0`, with `parentBundleId`/`bundleIndex`/`bundleTotalCalls` set) and triggers the standard single-tx confirmation popup.
4. The single-tx popup (`TransactionConfirmation.tsx`) sees `parentBundleId` on the request and:
   - Renders a "Split batch — Step N of M" badge above the transaction info card.
   - For `bundleIndex > 0`, the `useSplitPriorTxState` hook subscribes to `txHistoryUpdated` for the prior split tx id and keeps the Confirm button disabled with an explanatory banner ("Waiting for previous transaction to confirm…" / "Estimating gas with new chain state…") until the prior tx flips to `success`.
   - When the prior tx resolves, `gasEstimateKey` increments and `GasEstimateDisplay` remounts, forcing a fresh `eth_estimateGas` against the post-prior-tx chain state.
5. After call N broadcasts and finalizes, `applyReceiptToHistory` (in `txReceiptPoller.ts`) looks up the tx in history; if it carries `parentBundleId`, it calls `advanceSplitBundle` in `splitBatchSequencer.ts`. The sequencer:
   - Appends the txHash to `BundleStatus.txHashes` and a coerced `BundleReceipt` to `BundleStatus.receipts`.
   - On success: increments `splitNextIndex` and queues the next call (or finalizes the bundle as `CONFIRMED` if the queue is empty).
   - On revert / drop: marks the bundle as `PARTIAL_REVERT` (if any prior call succeeded) or `REVERTED`. No further calls queued.
   - On user rejection / pre-broadcast failure (hooked from `handleRejectTransaction` and `handleTransactionFailure` in `txHandlers.ts`): marks the bundle as `OFFCHAIN_FAILURE` (`PARTIAL_REVERT` if any prior succeeded).
6. Throughout, `wallet_getCallsStatus` returns the same `BundleStatus` shape as a normal non-atomic batch — receipts accumulate, status reflects the aggregate. The dapp doesn't need to know split mode happened.

**Idempotency:** `advanceSplitBundle` short-circuits if `splitNextIndex > bundleIndex`, defending against duplicate finalizations (sync send + an opportunistic poll arriving for the same tx).

## Message Flow

### wallet_sendCalls (full lifecycle)

```
1. Dapp calls provider.request({ method: "wallet_sendCalls", params: [...] })

2. impersonator.ts (inpage)
   - Creates request UUID, sends i_walletSendCalls via window.postMessage
   - Waits for walletSendCallsResult

3. inject.ts (content script)
   - Generates bundleId (UUID — never dapp-controlled)
   - Starts waitForStorageResult("batchTxAck:{bundleId}")
   - Fires chrome.runtime.sendMessage({ type: "walletSendCalls", bundleId, params, origin, favicon })

4. background.ts (service worker)
   - Routes to handleWalletSendCalls() in batchTxHandlers.ts

5. batchTxHandlers.ts
   - Validates params (version, chainId, account type, from address)
   - Saves PendingBatchTxRequest to pendingBatchTxStorage (includes accountType)
   - Creates initial BundleStatus (status: 100, atomic: true for Bankr / false for PK/SP)
   - Writes ack to chrome.storage.local("batchTxAck:{bundleId}")
   - Opens popup via openExtensionPopup()

6. inject.ts picks up ack → posts walletSendCallsResult to impersonator.ts
7. impersonator.ts resolves with { id: bundleId }
8. Dapp receives the bundle ID, can now poll wallet_getCallsStatus

9. Popup renders BatchTransactionConfirmation.tsx
   - Shows collapsible call cards with decoded function names
   - Shows asset changes (via simulateBatchAssetChanges or simulateBatchAssetChangesNonAtomic)
   - Shows "Auto-Sequential" badge for PK/SP accounts
   - Gas estimation: sequential via estimateBatchGasSequential for non-atomic, single encoded batch for atomic
   - Shows Tenderly simulation link

10. User clicks Confirm
    A) Bankr/impersonator (atomic):
       - Sends confirmBatchTransactionAsync message
       - Encodes calls via ERC-7821, submits single tx to Bankr API
       - On direct success, retries raw receipt enrichment asynchronously to populate tx-history `assetChanges`; an immediately available raw receipt is sanitized before storing it for `wallet_getCallsStatus`
       - Updates BundleStatus (200/400/500)
    B) PK/SP (non-atomic):
       - Sends confirmBatchTransactionAsyncPK message (includes pre-computed gasEstimates)
       - Decrypts private key from vault
       - Phase 1: assigns sequential nonces via getNextNonce()
       - Uses pre-computed gas estimates (or re-estimates if not provided)
       - Phase 2: signs + broadcasts each call with gas+fee params (zero RPC calls during broadcast)
       - trackNonAtomicBundleCompletion() polls receipts and computes aggregate BundleStatus
    - Both paths: writes batchTxResult, shows notification, saves to txHistory

11. User clicks Reject
    - Updates BundleStatus to 400 ("User rejected")
    - Writes rejection to batchTxResult storage
```

## ERC-7821 Batch Encoding

Bankr wallet addresses are smart accounts that support ERC-7821 batch execution. Multiple calls are encoded into a single transaction:

```
to:    walletAddress (calls itself)
value: sum of all call values
data:  execute(BATCH_MODE, encodedCalls)
```

**Encoding logic** (in `batchTxHandlers.ts → encodeBatchCalls()`):

```typescript
const ERC7821_ABI = [{
  name: "execute",
  inputs: [
    { name: "mode", type: "bytes32" },
    { name: "executionData", type: "bytes" },
  ],
  stateMutability: "payable",
  type: "function",
}];

const ERC7821_BATCH_MODE =
  "0x0100000000007821000100000000000000000000000000000000000000000000";

// 1. Encode calls as tuple[] → (address to, uint256 value, bytes data)[]
const executionData = encodeAbiParameters(
  [{ type: "tuple[]", components: [
    { type: "address", name: "to" },
    { type: "uint256", name: "value" },
    { type: "bytes", name: "data" },
  ]}],
  [calls],
);

// 2. Encode the execute function call
const calldata = encodeFunctionData({
  abi: ERC7821_ABI,
  functionName: "execute",
  args: [ERC7821_BATCH_MODE, executionData],
});
```

This same encoding pattern is used in the website admin page (`AdminContent.tsx`) for the Clanker Fee batch claim.

## Non-Atomic Batching (PK/SP EOA Accounts)

### How It Works

When a PK/SP account confirms a batch, each call becomes a separate onchain transaction:

```
handleConfirmBatchTransactionPK(bundleId, password, precomputedGasEstimates)
  → Decrypt private key (same vault/session pattern as single-tx PK handler)
  → processBatchTransactionNonAtomicInBackground()
    Phase 1 (sequential): for each call
      → getNextNonce(address, chainId)  // increments cache each time
      → addTxToHistory("processing")
      → push to prepared[]
    Gas estimation:
      → Use precomputedGasEstimates from UI (avoids duplicate RPC calls)
      → Or call estimateBatchGasSequential() if not provided
    Phase 2 (concurrent broadcast): for each prepared item
      → signAndBroadcastTransaction(privateKey, tx with gas+fee params)
      → updateTxInHistory("pending")
      → startReceiptPolling() per tx (exponential backoff 2s→30s)
    Tracking:
      → trackNonAtomicBundleCompletion() polls LOCAL STORAGE (no RPC) for tx status
      → startReceiptPolling handles actual RPC receipt checks with backoff
      → Only updates BundleStatus once ALL txs resolve (prevents partial receipt leaks)
      → Computes aggregate: CONFIRMED(200) / PARTIAL_REVERT(600) / REVERTED(500)
      → Sets txHash to LAST successful tx (the meaningful action, e.g., swap)
      → Receipts reversed in response (last tx first) for dapp compatibility
```

**Nonce management**: Uses the same `nonceManager.ts` pattern as the approve+swap flow in `handleExecuteSwapDirect()`. Each `getNextNonce()` call increments the in-memory cache, guaranteeing sequential nonces even when calls are rapid-fire.

**Individual tx IDs**: Each call gets a tx ID of `{bundleId}:{index}` (e.g., `abc-123:0`, `abc-123:1`). These are stored in tx history individually. The `BundleStatus` stores all tx hashes in `txHashes[]`.

**Primary tx hash**: The `BundleStatus.txHash` is set to the **last** successful tx hash (e.g., swap after approve), since that's the meaningful action the user and dapp care about.

### Gas Estimation for Sequential Calls

**Problem**: Individual `eth_estimateGas` calls fail for dependent calls (e.g., a swap that needs a prior approve) because each is simulated independently without prior state changes.

**Solution** (`batchGasEstimation.ts → estimateBatchGasSequential()`) — three-tier fall-through:

1. **Tier 1: `eth_simulateV1`** — fastest path. Simulates all calls sequentially in one RPC call, returns `gasUsed` per call. State persists between calls so the swap sees the approve's allowance. Per-chain support cached with 10-min TTL. Supported on Geth 1.14.9+, Reth, Nethermind, Besu, and Alchemy. When unsupported (or when the RPC returns an error mid-call) we fall through to tier 2.
2. **Tier 2: TxSimulator bytecode injection** — universal fallback. Same pattern as the asset-changes simulation: inject `TxSimulator.sol` runtime bytecode at the user's address via `eth_call` state override and call `simulateBatchGas()`. The simulator runs all calls sequentially (state persists, `msg.sender == user`) and measures gas per call via `gasleft()` deltas, then adds intrinsic (21000) + calldata cost in-contract so the returned values are usable directly as tx gas limits after a 20% buffer. Works on **any chain that supports `eth_call` state overrides** (Berlin+), so realistically every modern L1/L2.
3. **Tier 3 (last resort): Individual estimation with hardcoded buffer** — only hits when both tier 1 and tier 2 fail. Estimates each call independently via `eth_estimateGas`; dependent calls that fail get a 500K gas buffer. Onchain execution is still correct because nonce ordering ensures approve processes first, but this is the only path that surfaces a `fallbackUsed: true` warning to the UI.

**`fallbackUsed` flag**: Each `GasEstimate` returned by `estimateBatchGasSequential` has a `fallbackUsed?: boolean` field. It's `true` when the estimate came from a hardcoded fallback rather than a real eth call:
- 500k from `estimateIndividualWithFallback` (tier 3) when a dependent call's `eth_estimateGas` fails
- 200k from `tryEthSimulateV1` when an `eth_simulateV1` result is missing the `gasUsed` field (rare)

After the tier-2 path was added, `fallbackUsed` should be **near-extinct in practice** — it only triggers when a chain supports neither `eth_simulateV1` nor `eth_call` state overrides, which is essentially nothing modern. The yellow warning banner and per-row editing UI is kept for the rare case it does happen, plus the user-editable gas-limit inputs remain available regardless of tier so power users can override even on a successful estimate.

Normal batching treats this as informational — the onchain execution works regardless because of nonce ordering — but the UI surfaces it so power users can override it. The fallback warning banner subtitle reads "Edit highlighted row below if your call needs more. Extra gas gets refunded back." (normal batches) or "Edit highlighted row below — too high wastes L1 burn, too low reverts on L2 (burn lost)." (force inclusion batches, where overpayment is permanent). For force inclusion the stakes are much higher; see `_docs/L2_FORCE_INCLUSION.md`.

**User-editable gas limits (PK/Seed non-atomic batches)**: `MultiTxGasEstimateDisplay` renders an expanded "Gas Limit (per call)" section with an editable input per call. When any estimate has `fallbackUsed: true`:

- The gas section auto-expands
- A yellow Bauhaus warning banner appears above the gas box
- Affected rows are highlighted (warning icon, bold label, yellow input border)
- Each row has an external-link icon that opens `${explorer}/address/${call.to}` so the user can sanity-check typical gas on past txs

User edits flow through `onGasEstimates → cachedGasEstimates` → confirm message → background handler → signing. Bankr atomic batches are not editable (Bankr manages gas server-side).

**RPC call optimization**: Gas estimates are computed ONCE in the UI (`MultiTxGasEstimateDisplay` → `onGasEstimates` callback) and passed to the background handler via the confirm message (`precomputedGasEstimates`). This avoids duplicate RPC calls.

**Broadcast with zero RPC calls**: Phase 2 provides `gas`, `maxFeePerGas`, and `maxPriorityFeePerGas` on every tx so viem's `sendTransaction` only calls `eth_sendRawTransaction` — no fee estimation or gas estimation during broadcast. This prevents 429 rate limiting from breaking the broadcast.

### Bundle Status for Non-Atomic

- `atomic: false` — tells dapp this was non-atomic
- `txHash: string` — last successful tx hash (the meaningful action)
- `txHashes: string[]` — all tx hashes (one per call)
- `receipts: BundleReceipt[]` — one per call, only populated when ALL txs resolve
- Aggregate status:
  - `200` (CONFIRMED) — all txs confirmed
  - `500` (REVERTED) — all txs reverted
  - `600` (PARTIAL_REVERT) — some succeeded, some reverted

### Key Differences from Atomic Path

| Aspect | Atomic (Bankr) | Non-Atomic (PK/SP) |
|---|---|---|
| Onchain txs | 1 (ERC-7821 encoded) | N (one per call) |
| Nonce | Single (API-managed) | Sequential (nonceManager) |
| Atomicity | All-or-nothing | Each call independent |
| Gas estimation | Single batch tx | Sequential (eth_simulateV1 → fallback) |
| Confirm message | `confirmBatchTransactionAsync` | `confirmBatchTransactionAsyncPK` |
| Simulation message | `simulateBatchAssetChanges` | `simulateBatchAssetChangesNonAtomic` |
| Bundle txHash | The single tx hash | Last successful tx hash |
| Receipt polling | Individual `startReceiptPolling` | Per-tx `startReceiptPolling` + `trackNonAtomicBundleCompletion` (local storage) |
| Bundle status | 200 or 500 | 200, 500, or 600 |

## Simulation & Tenderly

### Atomic Batch Simulation (Bankr Accounts)

Batch transactions are **self-calls** (`from === to = wallet address`) for ERC-7821 execution. This breaks the normal simulation approach because the state override replaces the wallet's code with the simulator bytecode, making the self-call hit the simulator instead of the smart account.

**Solution**: `TxSimulator.sol` has a dedicated `simulateBatch()` function that executes all calls **sequentially within a single `eth_call`**. This preserves state between calls (e.g., an `approve` in call 1 persists for the `swap` in call 2).

```
BatchTransactionConfirmation passes batchCalls[] to AssetChangesDisplay
  → AssetChangesDisplay sends "simulateBatchAssetChanges" message
    → background calls simulateBatchAssetChanges() in txSimulation.ts
      → createAccessList per call (parallel) → merge candidate addresses
      → encodeFunctionData(simulateBatch, [calls, candidates])
      → eth_call with state override: simulator bytecode at wallet address
      → Simulator executes all calls sequentially, snapshots balances before/after
      → Returns cumulative (ethDelta, tokens[], deltas[])
      → enrichTokenChanges() for metadata + prices
```

**Why this works**: The simulator is deployed at the wallet address, so `msg.sender` for each call is the wallet address (approvals go to the right place), and `address(this)` gives real `balanceOf` results.

**Key constraint**: When updating `TxSimulator.sol`, you must recompile (`forge build`) and copy the **exact** `deployedBytecode.object` from `out/TxSimulator.sol/TxSimulator.json` into `SIMULATOR_BYTECODE` in `txSimulation.ts`. A bytecode mismatch (even from a different compilation run) causes `InvalidJump` EVM errors because jump offsets differ.

### Non-Atomic Batch Simulation (PK/SP Accounts)

For EOA accounts, asset change simulation uses a two-tier approach:

```
AssetChangesDisplay sends "simulateBatchAssetChangesNonAtomic" message
  → background calls simulateBatchAssetChangesNonAtomic()
    → Run eth_simulateV1 and simulateBatchAssetChanges() in parallel
    → Merge transfer-log deltas from eth_simulateV1 with NFT/revert data from bytecode injection
```

**`eth_simulateV1` transfer-log path** (Geth 1.14.9+, Sept 2024; also Reth, Nethermind, Besu):
- Natively simulates multiple txs sequentially with state persistence between calls
- Uses `traceTransfers: true` for synthetic native ETH transfer events
- Parses ERC-20 `Transfer` event logs to compute net balance changes per token
- Provides ERC-20/native deltas when available, but its revert verdict is not authoritative
- Per-chain support cached in memory with 10-min TTL (avoids retrying unsupported RPCs)

**Bytecode injection** (same as atomic path):
- Per-call `eth_createAccessList` for candidate discovery (may miss cross-call dependencies)
- Bytecode injection at user's address replaces EOA code
- `simulateBatch()` executes all calls sequentially — balance diffing is accurate
- Works on any Berlin+ chain (universal compatibility)
- Owns the final `txSuccess` verdict when both paths complete. Alchemy Base has returned false-positive `eth_simulateV1` reverts for valid approve + 0x AllowanceHolder swap batches, while the bytecode path matched real broadcasts.

**Why both**: `eth_simulateV1` is useful for transfer-log deltas and isn't universally supported yet. The bytecode injection approach works everywhere, captures NFTs/post-tx tokenURI data, and is the source of truth for the simulated revert banner.

### Tenderly

**Atomic batches only.** For Bankr/impersonator accounts, the Tenderly button uses the **encoded ERC-7821 batch calldata** (the actual onchain transaction format). The `BatchTransactionConfirmation` component builds the simulator URL from:

- `contractAddress` = wallet address (self-call)
- `rawFunctionInput` = ERC-7821 encoded batch (`execute(BATCH_MODE, executionData)`)
- `value` = sum of all call values

**Hidden for non-atomic (PK/SP) batches.** Tenderly's dashboard simulator URL (`dashboard.tenderly.co/simulator/new`) only accepts a single tx — there is no shareable URL form for bundles. Tenderly does support bundled simulation, but only via [`tenderly_simulateBundle`](https://docs.tenderly.co/simulations/bundled-simulations) RPC and the `simulate-bundle` REST endpoint, neither of which is a shareable link. For EOA non-atomic batches, the encoded self-call to the EOA would be misleading (the EOA has no code and doesn't support ERC-7821), so the Simulate on Tenderly button is hidden entirely on the auto-sequential confirmation screen. This may change once EIP-7702 atomic batching lands for EOAs.

## Storage Keys

| Key | Shape | Retention |
|---|---|---|
| `pendingBatchTxRequests` | `PendingBatchTxRequest[]` (includes `accountType`) | 30-minute expiry |
| `bundleStatuses` | `BundleStatus[]` (includes `txHashes[]`, `txHash` = last successful) | 24 hours, max 100 entries |
| `batchTxResult:{bundleId}` | `{ result, timestamp }` | Transient, 30-min stale cleanup |
| `batchTxAck:{bundleId}` | `{ result: { id }, timestamp }` | Transient, 30-min stale cleanup |
| `capabilitiesResult:{id}` | `{ result, timestamp }` | Transient, 30-min stale cleanup |
| `callsStatusResult:{id}` | `{ result, timestamp }` | Transient, 30-min stale cleanup |

`bundleStatuses` is a single array in `chrome.storage.local`, so all writes
through `bundleStatusStorage.ts` are serialized with an in-process lock. This
matters for cross-dapp batches: one confirmed onchain tx may need to terminal-
update several source `wallet_sendCalls` bundle IDs at once, and parallel
read-modify-write updates would otherwise clobber all but the last status.

## Bundle Status State Machine

```
wallet_sendCalls received → status: 100 (pending), atomic: true/false

Atomic (Bankr):
  ├── User confirms
  │     ├── Tx confirmed onchain  → 200
  │     ├── Tx reverted onchain   → 500
  │     └── Submission failed       → 400
  ├── User rejects                  → 400
  └── Request expires (30 min)      → 400

Non-Atomic (PK/SP):
  ├── User confirms
  │     ├── All txs confirmed       → 200
  │     ├── All txs reverted        → 500
  │     ├── Mixed (some reverted)   → 600 (PARTIAL_REVERT)
  │     └── All broadcasts failed   → 400
  ├── User rejects                  → 400
  └── Request expires (30 min)      → 400
```

## Confirmation UI

`BatchTransactionConfirmation.tsx` renders:

1. **Header** — Back, navigation (if multiple pending requests), Reject All
2. **"Batch Transaction (N calls)"** banner (bauhaus.blue) + **"Auto-Sequential" badge** (bauhaus.yellow) for PK/SP
3. **Info card** — Origin (with favicon), From account, Network badge
   - **Force inclusion gear icon** appears next to the Network badge when `isForceInclusionSupportedForAccount(chainId, accountType)` returns true: the chain must be an OP Stack chain with a portal contract, the account can't be an Impersonator, AND for Bankr accounts the L1 chain (e.g. Ethereum mainnet) must be in `BANKR_SUPPORTED_CHAIN_IDS` since Bankr API submits the L1 deposit on their end. Clicking toggles a collapsible force inclusion toggle. When enabled: network badge appends "via Ethereum/Sepolia", gas re-estimates for the L1 deposit path. See `_docs/L2_FORCE_INCLUSION.md`.
4. **Calls list** — Collapsible cards, collapsed by default:
   - **Collapsed**: Call index badge, decoded function name (via `CalldataDecoder`), truncated `to` address
   - **Expanded**: Full `to` address (with copy/explorer), value, decoded calldata
   - **Built-in clear-signing layout** (ERC-20 transfer / approve via `BuiltinExpandedContent`): the descriptor card is the headline; TO + raw decoder + digest collapse behind a single "Calldata" disclosure
   - **Editable approve amount** — approve CallCards render an inline `EditApproveAmountRow` editor. Saving sends `updateCallInPendingBatch` (default) or `updateCallInCrossDappBatch` (cross-dapp wrapper override via `onEditCallData` prop). The mutation rewrites `params.calls[i].data` (or `entries[i].tx.data`) in storage; the popup's storage listener pushes the fresh request into the confirmation, the synthetic batch tx + per-call gas inputs re-derive from the new `calls[]`, and `AssetChangesDisplay` / `MultiTxGasEstimateDisplay` re-fire on their data-keyed effects. Sign-time handlers (`handleConfirmBatchTransaction`, `handleConfirmBatchTransactionPK`, `handleConfirmCrossDappBatch`) all re-fetch the latest storage snapshot, so the edited calldata flows through without any per-handler plumbing. A future EIP-7702 atomic path for PK/SP that calls `encodeBatchCalls(pending.params.calls, ...)` inherits the same property automatically.
   - Left border accent cycles through bauhaus colors (red, blue, yellow)
5. **Asset Changes** — Reused `AssetChangesDisplay`:
   - Atomic: `simulateBatchAssetChanges` (bytecode injection)
   - Non-atomic: `simulateBatchAssetChangesNonAtomic` (eth_simulateV1 deltas + bytecode-injection verdict/NFTs)
6. **Gas Estimates** — `MultiTxGasEstimateDisplay`:
   - Atomic: single batch tx gas estimate (via `batchedTx` prop)
   - Non-atomic: sequential per-call estimates via `estimateBatchGasSequential` (`isNonAtomic` prop)
   - Force inclusion (non-atomic): fetches L1 cost via `estimateForceInclusionGas` AND L2 `_gasLimit` via `estimateBatchGasSequential` in parallel
   - Per-call editable gas limit inputs for PK/Seed accounts; auto-expands + shows yellow warning banner when `fallbackUsed` detected on any estimate
   - Estimates are cached via `onGasEstimates` callback and passed to the confirm handler (including when force inclusion is active)
7. **Tenderly link** — Using encoded batch tx params
8. **Confirm/Reject buttons** — Confirm routes to `confirmBatchTransactionAsync` / `confirmBatchTransactionAsyncPK` (with an additional `forceInclusion: true` flag when enabled)
9. **Force inclusion progress screen** — For atomic (Bankr) force inclusion batches, the popup stays open and shows `ForceInclusionProgress` after confirm. Non-atomic force inclusion batches close the popup after broadcast and track sub-txs in the activity feed (same as normal non-atomic behavior).

## Account-Based Batching Strategy

The routing decision is based on `account.type` (stored on `PendingBatchTxRequest.accountType`):

```
account.type === "bankr" | "impersonator"  →  Atomic (ERC-7821 → Bankr API)
account.type === "privateKey" | "seedPhrase"  →  Auto-Sequential (nonces → individual txs)
  └─ Future: if 7702 delegation active  →  Atomic (ERC-7821 + authorizationList)
```

This design ensures all three strategies coexist without breaking each other. When EIP-7702 is added, it'll be a third branch inside the PK/SP path — checking if the EOA has an active delegation before deciding atomic vs auto-sequential.

## RPC Call Optimization

### Problem: Rate Limiting on Free RPCs

The batch flow makes multiple RPC calls (simulation, gas estimation, fee estimation, balance checks) that can trigger 429 rate limiting on free public RPCs like `mainnet.base.org`.

### Solutions Implemented

1. **Gas estimates computed once** — `MultiTxGasEstimateDisplay` computes gas via `estimateBatchGasSequential`, caches the result, and passes it to the confirm handler via the message. The background handler uses precomputed estimates instead of re-estimating.

2. **Zero RPC calls during broadcast** — Phase 2 provides `gas`, `maxFeePerGas`, and `maxPriorityFeePerGas` on every tx so viem's `sendTransaction` only calls `eth_sendRawTransaction`.

3. **eth_simulateV1 support caching** — Per-chain support is cached with 10-min TTL. After first failure (method not found), subsequent calls skip directly to fallback.

4. **Debounced portfolio refresh** — `PortfolioTabs` debounces `txHistoryUpdated` messages so multiple rapid updates (from batch tx history writes) collapse into a single portfolio refresh after the 3-second delay.

5. **Deduplicated receipt polling** — Non-atomic batch calls use `startReceiptPolling` per tx (exponential backoff 2s→30s). `trackNonAtomicBundleCompletion` monitors local storage (zero RPC) for status changes, then updates `BundleStatus` once all txs resolve. Frontend polling (`TxStatusList.checkPendingTxReceipt`) skips txs with active background pollers to prevent duplicate RPC calls.

6. **Reversed receipts for dapp compatibility** — `wallet_getCallsStatus` returns receipts with the last call's receipt first. Dapps like LlamaSwap use `receipts.find()` to pick the explorer link tx hash, which returns the first match — reversing ensures they show the meaningful tx (swap) instead of the approve.

## EIP-7702 Atomic Batching for PK/SP Accounts

Shipped — see [`7702.md`](./7702.md) for the canonical reference (default delegate, resolution order, settings UI, message types, MM version-upgrade policy).

Quick summary as it relates to ERC-5792:

- `handleConfirmBatchTransactionPK` now branches by `resolveActiveDelegate()`:
  - `calls.length === 1` → single normal tx (no ERC-7821 wrap).
  - delegate resolves → `processBatchTransactionAtomic7702InBackground` (one type-4 tx, one onchain hash, ERC-7821 calldata via the same `encodeBatchCalls()`).
  - else → `processBatchTransactionNonAtomicInBackground` (existing auto-sequential).
- Cross-dapp + user-assembled batches are unlocked for PK/SP on 7702-supported chains via `shipCrossDappBatchPkSp` (lives in `crossDappBatchHandlers.ts`).
- `BatchTransactionConfirmation.tsx` flips `isNonAtomic` to false when the resolver returns a usable delegate, hiding the "Auto-Sequential" badge and exposing the Tenderly Simulate button. An authorization banner shows when `needsAuthorization = true` (first batch on a chain).

## Cross-Dapp Batching (User-Assembled)

### What it is

A second batching path where **the user is the assembler**. The user can pull in BOTH single `eth_sendTransaction` requests AND entire dapp-initiated `wallet_sendCalls` bundles, mix them across dapps, and ship the whole thing as one onchain tx:

1. **Source A — single tx**: dapp sends `eth_sendTransaction`. On the standard transaction confirmation screen, the user clicks **"+ Batch"**. The request is moved out of `pendingTxRequests` into a single `crossDappBatch` storage entry; the dapp's promise stays open (no `txResult:{txId}` write yet).
2. **Source B — dapp-initiated bundle**: dapp sends `wallet_sendCalls`. On the BatchTransactionConfirmation screen, the user clicks **"+ Batch"**. Every call from that bundle is appended to `crossDappBatch` (siblings share a `bundleId`); the dapp already has its bundle id (returned via the immediate `batchTxAck` write) and is now polling `wallet_getCallsStatus` — its `bundleStatuses` entry stays at `PENDING (100)` while the calls live in the cross-dapp batch.
3. The user can continue to other dapps (or in-wallet flows) and add more.
4. When ready, the user opens the batch from the homepage banner and clicks Confirm.
5. We encode all calls with the same `encodeBatchCalls()` used by `wallet_sendCalls`, ship a single tx via Bankr API or PK/SP EIP-7702 local signing, and fan the resulting tx hash out to every entry:
   - **eth_sendTransaction entries** → write `txResult:{txId} = { success: true, txHash }`. inject.ts in each tab picks it up and resolves the dapp's `eth_sendTransaction` promise.
   - **wallet_sendCalls entries** → keep `bundleStatuses` PENDING with the shared `txHash` until the atomic tx receipt is terminal, then update every source bundle to CONFIRMED or REVERTED (deduped per unique bundle).
   - The single `txHistory` entry records `batchCallOrigins: [{ origin, favicon }]` in call order so the Activity transaction-details modal can render the original dapp favicon + hostname for each decoded ERC-7821 call.

### Eligibility

- **Bankr** (atomic via API) or **PK/SP** (atomic via EIP-7702 type-4 tx whenever `resolveActiveDelegate` finds a usable onchain/default delegate). Impersonator (view-only) is still excluded. See [`7702.md`](./7702.md) for the resolution rules.
- **One batch at a time**, locked to the `from` address + `chainId` of the first tx added. The "Add to Batch" button is disabled with a tooltip when the next tx request mismatches.

### Storage shape

`chrome.storage.local.crossDappBatch`:

```typescript
{
  fromAddress: string,
  chainId: number,
  chainName: string,
  accountType: "bankr" | "privateKey" | "seedPhrase",
  entries: Array<{
    txId: string,                  // entry id within the batch (used for individual removal)
    tx: TransactionParams,         // {from, to, data, value, chainId}
    origin: string,                // dapp origin
    favicon: string | null,
    addedAt: number,
    source?:                       // how this entry got into the batch (default: eth_sendTransaction)
      | { kind: "eth_sendTransaction" }
      | { kind: "wallet_sendCalls", bundleId: string, callIndex: number, totalCalls: number },
  }>,
  createdAt: number,
}
```

For `eth_sendTransaction` entries `txId` matches the original `PendingTxRequest.id`. For `wallet_sendCalls` entries `txId` is a synthetic `${bundleId}:${callIndex}`; the parent `bundleId` lives in `source` so siblings can be looked up together.

### Message types (extension-only — popup → background)

| Message                       | Handler                              | Notes                                                                                                       |
| ----------------------------- | ------------------------------------ | ----------------------------------------------------------------------------------------------------------- |
| `addToCrossDappBatch`         | `handleAddToCrossDappBatch(txId)`    | Adds a single `eth_sendTransaction` request. Validates account/chain/from, moves the request out of `pendingTxRequests`, dapp promise kept open. |
| `addCallsToCrossDappBatch`    | `handleAddCallsToCrossDappBatch(bundleId)` | Adds an entire dapp-initiated `wallet_sendCalls` bundle. Each call becomes one entry; siblings share `source.bundleId`. Removes the request from `pendingBatchTxRequests`; the bundle's `bundleStatuses` entry stays at PENDING (the dapp keeps polling). |
| `removeFromCrossDappBatch`    | `handleRemoveFromCrossDappBatch(txId)` | For `eth_sendTransaction` entries: writes `txResult:{txId}` rejection. For `wallet_sendCalls` entries: removes ALL siblings from the same bundle and updates `bundleStatuses` to OFFCHAIN_FAILURE once. Clears batch if empty. |
| `rejectCrossDappBatch`        | `handleRejectCrossDappBatch()`       | Fans rejection to every entry — `txResult:{txId}` for plain entries, deduped `bundleStatuses` updates for bundle entries. Clears the batch. |
| `confirmCrossDappBatch`       | `handleConfirmCrossDappBatch(password, gasEstimates?)` | Encodes via `encodeBatchCalls()`, ships via Bankr API or PK/SP EIP-7702 local signing. Plain entries get the shared tx hash immediately; bundle entries stay PENDING until receipt and then update to CONFIRMED/REVERTED. |

All five are gated by `EXTENSION_ONLY_MESSAGES` in `background.ts`.

### Lifecycle

```
1. Dapp A → eth_sendTransaction → standard pendingTxRequest created.
2. User clicks "+ Add to Batch" on the confirmation screen.
3. Background: handleAddToCrossDappBatch
   - validates active account is bankr/impersonator
   - validates chain is in BANKR_SUPPORTED_CHAIN_IDS
   - validates from + chainId match the existing batch (if any)
   - appends entry to crossDappBatch storage
   - removePendingTxRequest(txId) — Dapp A is still waiting (no txResult written)
4. User can repeat for Dapps B, C, ... (or in-wallet transfers — they go through
   the same pendingTxRequests path).
5. User opens the batch from the homepage banner → CrossDappBatchConfirmation.
   - Renders BatchTransactionConfirmation underneath with onRemoveCall +
     per-call origin chips. Soft yellow tint on the page bg + a yellow accent
     strip across the top make this screen visually distinct from the
     standard dapp batch confirmation. Confirm button reads "Confirm Batch".
6. Hover a call → tiny trash button fades in on the right edge of that call
   (absolute positioning so it doesn't shift the layout). Click → removeFromCrossDappBatch
   - That dapp's request is rejected immediately, batch shrinks.
   - If batch now empty, it is cleared and the user goes back to main.
7. Click Reject → rejectCrossDappBatch fans rejection to every dapp.
8. Click Confirm Batch → confirmCrossDappBatch
   - Resolves API key (cached → session restoration → password decrypt).
   - encodeBatchCalls(entries → ERC5792Call[]) → single ERC-7821 tx.
   - submitTransactionDirect(apiKey, tx) — same path as wallet_sendCalls atomic.
   - On success: writes txResult:{txId} = { success: true, txHash } for EVERY
     entry. inject.ts in each tab picks up its own txId via the storage listener
     and resolves the dapp's promise with the same hash.
   - On revert/error: same fan-out, but with a failure result.
   - Adds a single txHistory entry with `origin: "Cross-Dapp Batch"` and
     `functionName: "N calls"` so the activity tab shows it as a top-level
     "Cross-Dapp Batch" row with the call count as the secondary line.
   - Clears crossDappBatch.
   - Shows OS notification.
```

### Carousel and banner placement

- The cross-dapp batch is **always the first card** in the pending-requests carousel when it exists. `getCombinedRequests()` in `App.tsx` prepends it to the rest.
- It has its own dedicated view (`crossDappBatchConfirm`) that is reachable from:
  - The pending-requests banner on the homepage (when the cross-dapp batch is the only thing pending).
  - The pending-requests list (`pendingTxList`) — appears as the first card with a `YOUR BATCH` badge.
  - Carousel navigation arrows from any other tx/sig/batch confirmation screen.

### Add-to-Batch button placement

- **`TransactionConfirmation.tsx`** (single `eth_sendTransaction`): small inline yellow pill on the **right** side of the Tenderly simulation row, in the same place regardless of how many other requests are pending.
- **`BatchTransactionConfirmation.tsx`** (dapp `wallet_sendCalls`): same inline pill on the right of the Tenderly row. Hidden on the cross-dapp batch screen itself (the wrapper doesn't pass `onAddedToBatch`) and on PK/SP non-atomic batches.
- The button is **hidden entirely** when `accountType` is not `bankr` / `impersonator`.
- Disabled with tooltip when the active batch's `from` or `chainId` mismatches the current request.
- On click: the user is navigated directly to the cross-dapp batch confirmation screen so they immediately see the assembled batch.

### Why not PK/SP in v1

Plain EOA accounts can't execute multiple calls atomically without EIP-7702. The non-atomic batching path (`wallet_sendCalls` for PK/SP) already handles dapp-initiated batches by signing N txs concurrently — but that pattern doesn't help here, because the user-assembled batch would still need N signature popups to ship, providing no UX benefit over just confirming each tx individually. Once 7702 is wired up for PK/SP accounts, we can lift this restriction by reusing the same `crossDappBatchHandlers.ts` ship path with a 7702-style atomic submission.
