# ERC-5792 Batch Transaction Support

## Overview

ERC-5792 enables dapps to submit multiple calls as a batch transaction. WalletChan supports this for **all account types**:

| Account Type | Batching Mode | Strategy |
|---|---|---|
| `bankr` / `impersonator` | **Atomic** | ERC-7821 encoding → single tx via Bankr API |
| `privateKey` / `seedPhrase` | **Auto-Sequential** | Sequential nonces → individual txs broadcast concurrently |

Auto-sequential batching reduces wallet popups (single confirmation for N calls) and assigns sequential nonces automatically, providing a much better UX than N individual tx confirmations. In the future, EIP-7702 will enable atomic batching for EOA accounts as well.

**Spec**: https://eips.ethereum.org/EIPS/eip-5792

| `chrome/batchTxHandlers.ts` | Core handler logic, ERC-7821 encoding, PK/SP non-atomic handler |

## JSON-RPC Methods

### `wallet_getCapabilities(address, chainIds?)`

Returns per-chain capabilities. Both account types report `"supported"` so dapps show the batching option:

**Bankr/impersonator accounts** — on `BANKR_SUPPORTED_CHAIN_IDS`:
```json
{ "0x2105": { "atomic": { "status": "supported" } } }
```

**PK/SP accounts** — on all `ALLOWED_CHAIN_IDS`:
```json
{ "0x2105": { "atomic": { "status": "supported" } } }
```

**Why `"supported"` for EOAs**: The ERC-5792 spec treats `"unsupported"` the same as "no batching at all" — dapps hide the batching option entirely. By reporting `"supported"`, dapps show the batch UI. Execution is actually auto-sequential (individual txs with sequential nonces). The `atomicRequired` flag is ignored for EOA accounts — we always accept and execute non-atomically.

### `wallet_sendCalls({ version, chainId, calls, atomicRequired?, from?, id? })`

Receives a batch of calls and opens the confirmation popup. Returns `{ id }` immediately (the bundle ID). The dapp then polls `wallet_getCallsStatus` for the result.

**Validations performed:**
- `version` must be `"2.0.0"`
- `chainId` must be supported (Bankr chains for Bankr accounts, all `ALLOWED_CHAIN_IDS` for PK/SP)
- Active account must be `bankr`, `impersonator`, `privateKey`, or `seedPhrase`
- `from` (if provided) must match the active account address
- `atomicRequired` is ignored for PK/SP accounts (always executes non-atomically)

### `wallet_getCallsStatus(bundleId)`

Returns the bundle lifecycle status:

| Status | Meaning |
|---|---|
| `100` | Pending — awaiting user confirmation or tx not yet on-chain |
| `200` | Confirmed — tx included on-chain successfully |
| `400` | Offchain failure — user rejected, request expired, or submission error |
| `500` | Reverted — tx included on-chain but reverted |
| `600` | Partial revert — some txs succeeded, some reverted (non-atomic only) |

Response includes `receipts` array (with logs, gasUsed, txHash) when confirmed. For non-atomic batches, there is one receipt per call (in calls order). The `atomic` field is `false` for non-atomic bundles. The `txHash` field on `BundleStatus` is set to the **last successful tx** (e.g., the swap, not the approve) — this is what dapps typically show to users.

### `wallet_showCallsStatus(bundleId)`

Opens the block explorer for the bundle's primary transaction hash (last successful tx).

## Message Flow

### wallet_sendCalls (full lifecycle)

```
1. Dapp calls provider.request({ method: "wallet_sendCalls", params: [...] })

2. impersonator.ts (inpage)
   - Creates request UUID, sends i_walletSendCalls via window.postMessage
   - Waits for walletSendCallsResult

3. inject.ts (content script)
   - Generates bundleId (UUID — never dapp-controlled)
   - Starts waitForStorageResult("batchTxAck:{bundleId}")
   - Fires chrome.runtime.sendMessage({ type: "walletSendCalls", bundleId, params, origin, favicon })

4. background.ts (service worker)
   - Routes to handleWalletSendCalls() in batchTxHandlers.ts

5. batchTxHandlers.ts
   - Validates params (version, chainId, account type, from address)
   - Saves PendingBatchTxRequest to pendingBatchTxStorage (includes accountType)
   - Creates initial BundleStatus (status: 100, atomic: true for Bankr / false for PK/SP)
   - Writes ack to chrome.storage.local("batchTxAck:{bundleId}")
   - Opens popup via openExtensionPopup()

6. inject.ts picks up ack → posts walletSendCallsResult to impersonator.ts
7. impersonator.ts resolves with { id: bundleId }
8. Dapp receives the bundle ID, can now poll wallet_getCallsStatus

9. Popup renders BatchTransactionConfirmation.tsx
   - Shows collapsible call cards with decoded function names
   - Shows asset changes (via simulateBatchAssetChanges or simulateBatchAssetChangesNonAtomic)
   - Shows "Auto-Sequential" badge for PK/SP accounts
   - Gas estimation: sequential via estimateBatchGasSequential for non-atomic, single encoded batch for atomic
   - Shows Tenderly simulation link

10. User clicks Confirm
    A) Bankr/impersonator (atomic):
       - Sends confirmBatchTransactionAsync message
       - Encodes calls via ERC-7821, submits single tx to Bankr API
       - Updates BundleStatus (200/400/500)
    B) PK/SP (non-atomic):
       - Sends confirmBatchTransactionAsyncPK message (includes pre-computed gasEstimates)
       - Decrypts private key from vault
       - Phase 1: assigns sequential nonces via getNextNonce()
       - Uses pre-computed gas estimates (or re-estimates if not provided)
       - Phase 2: signs + broadcasts each call with gas+fee params (zero RPC calls during broadcast)
       - trackNonAtomicBundleCompletion() polls receipts and computes aggregate BundleStatus
    - Both paths: writes batchTxResult, shows notification, saves to txHistory

11. User clicks Reject
    - Updates BundleStatus to 400 ("User rejected")
    - Writes rejection to batchTxResult storage
```

## ERC-7821 Batch Encoding

Bankr wallet addresses are smart accounts that support ERC-7821 batch execution. Multiple calls are encoded into a single transaction:

```
to:    walletAddress (calls itself)
value: sum of all call values
data:  execute(BATCH_MODE, encodedCalls)
```

**Encoding logic** (in `batchTxHandlers.ts → encodeBatchCalls()`):

```typescript
const ERC7821_ABI = [{
  name: "execute",
  inputs: [
    { name: "mode", type: "bytes32" },
    { name: "executionData", type: "bytes" },
  ],
  stateMutability: "payable",
  type: "function",
}];

const ERC7821_BATCH_MODE =
  "0x0100000000007821000100000000000000000000000000000000000000000000";

// 1. Encode calls as tuple[] → (address to, uint256 value, bytes data)[]
const executionData = encodeAbiParameters(
  [{ type: "tuple[]", components: [
    { type: "address", name: "to" },
    { type: "uint256", name: "value" },
    { type: "bytes", name: "data" },
  ]}],
  [calls],
);

// 2. Encode the execute function call
const calldata = encodeFunctionData({
  abi: ERC7821_ABI,
  functionName: "execute",
  args: [ERC7821_BATCH_MODE, executionData],
});
```

This same encoding pattern is used in the website admin page (`AdminContent.tsx`) for the Clanker Fee batch claim.

## Non-Atomic Batching (PK/SP EOA Accounts)

### How It Works

When a PK/SP account confirms a batch, each call becomes a separate on-chain transaction:

```
handleConfirmBatchTransactionPK(bundleId, password, precomputedGasEstimates)
  → Decrypt private key (same vault/session pattern as single-tx PK handler)
  → processBatchTransactionNonAtomicInBackground()
    Phase 1 (sequential): for each call
      → getNextNonce(address, chainId)  // increments cache each time
      → addTxToHistory("processing")
      → push to prepared[]
    Gas estimation:
      → Use precomputedGasEstimates from UI (avoids duplicate RPC calls)
      → Or call estimateBatchGasSequential() if not provided
    Phase 2 (concurrent broadcast): for each prepared item
      → signAndBroadcastTransaction(privateKey, tx with gas+fee params)
      → updateTxInHistory("pending")
      → NO individual receipt polling (handled by trackNonAtomicBundleCompletion)
    Tracking:
      → trackNonAtomicBundleCompletion() polls ALL receipts
      → Only updates BundleStatus once ALL txs resolve (prevents partial receipt leaks)
      → Computes aggregate: CONFIRMED(200) / PARTIAL_REVERT(600) / REVERTED(500)
      → Sets txHash to LAST successful tx (the meaningful action, e.g., swap)
```

**Nonce management**: Uses the same `nonceManager.ts` pattern as the approve+swap flow in `handleExecuteSwapDirect()`. Each `getNextNonce()` call increments the in-memory cache, guaranteeing sequential nonces even when calls are rapid-fire.

**Individual tx IDs**: Each call gets a tx ID of `{bundleId}:{index}` (e.g., `abc-123:0`, `abc-123:1`). These are stored in tx history individually. The `BundleStatus` stores all tx hashes in `txHashes[]`.

**Primary tx hash**: The `BundleStatus.txHash` is set to the **last** successful tx hash (e.g., swap after approve), since that's the meaningful action the user and dapp care about.

### Gas Estimation for Sequential Calls

**Problem**: Individual `eth_estimateGas` calls fail for dependent calls (e.g., a swap that needs a prior approve) because each is simulated independently without prior state changes.

**Solution** (`batchGasEstimation.ts → estimateBatchGasSequential()`):

1. **Primary: `eth_simulateV1`** — simulates all calls sequentially in one RPC call, returns `gasUsed` per call. State persists between calls so the swap sees the approve's allowance.
2. **Fallback: Individual estimation with buffer** — estimate each call independently. Call 1 (approve) estimates normally. Dependent calls (swap) that fail get a generous 500K gas buffer. On-chain execution is correct regardless because nonce ordering ensures approve processes first.

**RPC call optimization**: Gas estimates are computed ONCE in the UI (`MultiTxGasEstimateDisplay` → `onGasEstimates` callback) and passed to the background handler via the confirm message (`precomputedGasEstimates`). This avoids duplicate RPC calls.

**Broadcast with zero RPC calls**: Phase 2 provides `gas`, `maxFeePerGas`, and `maxPriorityFeePerGas` on every tx so viem's `sendTransaction` only calls `eth_sendRawTransaction` — no fee estimation or gas estimation during broadcast. This prevents 429 rate limiting from breaking the broadcast.

### Bundle Status for Non-Atomic

- `atomic: false` — tells dapp this was non-atomic
- `txHash: string` — last successful tx hash (the meaningful action)
- `txHashes: string[]` — all tx hashes (one per call)
- `receipts: BundleReceipt[]` — one per call, only populated when ALL txs resolve
- Aggregate status:
  - `200` (CONFIRMED) — all txs confirmed
  - `500` (REVERTED) — all txs reverted
  - `600` (PARTIAL_REVERT) — some succeeded, some reverted

### Key Differences from Atomic Path

| Aspect | Atomic (Bankr) | Non-Atomic (PK/SP) |
|---|---|---|
| On-chain txs | 1 (ERC-7821 encoded) | N (one per call) |
| Nonce | Single (API-managed) | Sequential (nonceManager) |
| Atomicity | All-or-nothing | Each call independent |
| Gas estimation | Single batch tx | Sequential (eth_simulateV1 → fallback) |
| Confirm message | `confirmBatchTransactionAsync` | `confirmBatchTransactionAsyncPK` |
| Simulation message | `simulateBatchAssetChanges` | `simulateBatchAssetChangesNonAtomic` |
| Bundle txHash | The single tx hash | Last successful tx hash |
| Receipt polling | Individual `startReceiptPolling` | `trackNonAtomicBundleCompletion` (batch) |
| Bundle status | 200 or 500 | 200, 500, or 600 |

## Simulation & Tenderly

### Atomic Batch Simulation (Bankr Accounts)

Batch transactions are **self-calls** (`from === to = wallet address`) for ERC-7821 execution. This breaks the normal simulation approach because the state override replaces the wallet's code with the simulator bytecode, making the self-call hit the simulator instead of the smart account.

**Solution**: `TxSimulator.sol` has a dedicated `simulateBatch()` function that executes all calls **sequentially within a single `eth_call`**. This preserves state between calls (e.g., an `approve` in call 1 persists for the `swap` in call 2).

```
BatchTransactionConfirmation passes batchCalls[] to AssetChangesDisplay
  → AssetChangesDisplay sends "simulateBatchAssetChanges" message
    → background calls simulateBatchAssetChanges() in txSimulation.ts
      → createAccessList per call (parallel) → merge candidate addresses
      → encodeFunctionData(simulateBatch, [calls, candidates])
      → eth_call with state override: simulator bytecode at wallet address
      → Simulator executes all calls sequentially, snapshots balances before/after
      → Returns cumulative (ethDelta, tokens[], deltas[])
      → enrichTokenChanges() for metadata + prices
```

**Why this works**: The simulator is deployed at the wallet address, so `msg.sender` for each call is the wallet address (approvals go to the right place), and `address(this)` gives real `balanceOf` results.

**Key constraint**: When updating `TxSimulator.sol`, you must recompile (`forge build`) and copy the **exact** `deployedBytecode.object` from `out/TxSimulator.sol/TxSimulator.json` into `SIMULATOR_BYTECODE` in `txSimulation.ts`. A bytecode mismatch (even from a different compilation run) causes `InvalidJump` EVM errors because jump offsets differ.

### Non-Atomic Batch Simulation (PK/SP Accounts)

For EOA accounts, asset change simulation uses a two-tier approach:

```
AssetChangesDisplay sends "simulateBatchAssetChangesNonAtomic" message
  → background calls simulateBatchAssetChangesNonAtomic()
    → Try eth_simulateV1 first (primary)
    → Fallback to simulateBatchAssetChanges() (bytecode injection)
```

**Primary: `eth_simulateV1`** (Geth 1.14.9+, Sept 2024; also Reth, Nethermind, Besu):
- Natively simulates multiple txs sequentially with state persistence between calls
- Uses `traceTransfers: true` for synthetic native ETH transfer events
- Parses ERC-20 `Transfer` event logs to compute net balance changes per token
- No bytecode injection needed — cleaner and more reliable
- Per-chain support cached in memory with 10-min TTL (avoids retrying unsupported RPCs)

**Fallback: Bytecode injection** (same as atomic path):
- Per-call `eth_createAccessList` for candidate discovery (may miss cross-call dependencies)
- Bytecode injection at user's address replaces EOA code
- `simulateBatch()` executes all calls sequentially — balance diffing is accurate
- Works on any Berlin+ chain (universal compatibility)

**Why both**: `eth_simulateV1` isn't universally supported yet. The bytecode injection approach works everywhere but has slightly less robust candidate discovery for cross-call scenarios.

### Tenderly

Tenderly still uses the **encoded ERC-7821 batch calldata** (the actual on-chain transaction format). The `BatchTransactionConfirmation` component constructs a synthetic `PendingTxRequest` with:

- `to` = wallet address (self-call)
- `data` = ERC-7821 encoded batch
- `value` = sum of all call values

This synthetic request is used to build the Tenderly simulation URL.

## Bundle Status State Machine

```
wallet_sendCalls received → status: 100 (pending), atomic: true/false

Atomic (Bankr):
  ├── User confirms
  │     ├── Tx confirmed on-chain  → 200
  │     ├── Tx reverted on-chain   → 500
  │     └── Submission failed       → 400
  ├── User rejects                  → 400
  └── Request expires (30 min)      → 400

Non-Atomic (PK/SP):
  ├── User confirms
  │     ├── All txs confirmed       → 200
  │     ├── All txs reverted        → 500
  │     ├── Mixed (some reverted)   → 600 (PARTIAL_REVERT)
  │     └── All broadcasts failed   → 400
  ├── User rejects                  → 400
  └── Request expires (30 min)      → 400
```

`BatchTransactionConfirmation.tsx` renders:

1. **Header** — Back, navigation (if multiple pending requests), Reject All
2. **"Batch Transaction (N calls)"** banner (bauhaus.blue) + **"Auto-Sequential" badge** (bauhaus.yellow) for PK/SP
3. **Info card** — Origin (with favicon), From account, Network badge
4. **Calls list** — Collapsible cards, collapsed by default:
   - **Collapsed**: Call index badge, decoded function name (via `CalldataDecoder`), truncated `to` address
   - **Expanded**: Full `to` address (with copy/explorer), value, decoded calldata
   - Left border accent cycles through bauhaus colors (red, blue, yellow)
5. **Asset Changes** — Reused `AssetChangesDisplay`:
   - Atomic: `simulateBatchAssetChanges` (bytecode injection)
   - Non-atomic: `simulateBatchAssetChangesNonAtomic` (eth_simulateV1 → fallback)

   - Atomic: single batch tx gas estimate (via `batchedTx` prop)

8. **Confirm/Reject buttons** — Confirm routes to `confirmBatchTransactionAsync` or `confirmBatchTransactionAsyncPK`

## Account-Based Batching Strategy

The routing decision is based on `account.type` (stored on `PendingBatchTxRequest.accountType`):

```
account.type === "bankr" | "impersonator"  →  Atomic (ERC-7821 → Bankr API)
account.type === "privateKey" | "seedPhrase"  →  Auto-Sequential (nonces → individual txs)
  └─ Future: if 7702 delegation active  →  Atomic (ERC-7821 + authorizationList)
```

This design ensures all three strategies coexist without breaking each other. When EIP-7702 is added, it'll be a third branch inside the PK/SP path — checking if the EOA has an active delegation before deciding atomic vs auto-sequential.

## RPC Call Optimization

### Problem: Rate Limiting on Free RPCs

The batch flow makes multiple RPC calls (simulation, gas estimation, fee estimation, balance checks) that can trigger 429 rate limiting on free public RPCs like `mainnet.base.org`.

### Solutions Implemented

1. **Gas estimates computed once** — `MultiTxGasEstimateDisplay` computes gas via `estimateBatchGasSequential`, caches the result, and passes it to the confirm handler via the message. The background handler uses precomputed estimates instead of re-estimating.

2. **Zero RPC calls during broadcast** — Phase 2 provides `gas`, `maxFeePerGas`, and `maxPriorityFeePerGas` on every tx so viem's `sendTransaction` only calls `eth_sendRawTransaction`.

3. **eth_simulateV1 support caching** — Per-chain support is cached with 10-min TTL. After first failure (method not found), subsequent calls skip directly to fallback.

4. **Debounced portfolio refresh** — `PortfolioTabs` debounces `txHistoryUpdated` messages so multiple rapid updates (from batch tx history writes) collapse into a single portfolio refresh after the 3-second delay.

5. **No duplicate receipt polling** — Non-atomic batch calls don't start individual `startReceiptPolling`. Instead, `trackNonAtomicBundleCompletion` handles all receipt tracking and only updates `BundleStatus` once when ALL txs resolve.

## Future: EIP-7702 Atomic Batching for PK/SP Accounts

EIP-7702 allows EOA accounts to temporarily delegate to a smart contract implementation for a single transaction. This would upgrade PK/SP accounts from auto-sequential to atomic batching on supported chains.

### What's Already in Place

The non-atomic batching implementation provides the scaffolding for 7702:
- `handleConfirmBatchTransactionPK()` already exists — the 7702 path would be an additional branch inside it
- `confirmBatchTransactionAsyncPK` message type is already routed in `background.ts`
- UI already branches by account type, shows appropriate badges
- `encodeBatchCalls()` is account-type-agnostic (same ERC-7821 encoding for 7702)

### What Still Needs to Be Built

| File | Change |
|---|---|
| `chainRegistry.ts` | Add `isEip7702Supported` flag per chain, derive `EIP7702_CHAIN_IDS` set |
| `batchTxHandlers.ts` | Inside `handleConfirmBatchTransactionPK`, check 7702 support → encode as single ERC-7821 tx with authorizationList instead of sequential broadcasts |
| `handleWalletGetCapabilities` | (Already returns `"supported"` — no change needed) |
| `localSigner.ts` | Add EIP-7702 transaction construction using viem's `signAuthorization()` |
| `BatchTransactionConfirmation.tsx` | Remove "Auto-Sequential" badge when 7702 is active |

### EIP-7702 Transaction Shape

```typescript
{
  type: "eip7702",
  to: accountAddress,             // Self-call (ERC-7821 execute)
  data: encodedBatchCalldata,     // Same encodeBatchCalls() output
  value: totalValue,
  authorizationList: [{
    chainId,
    address: ERC7821_IMPLEMENTATION,  // Contract to delegate to
    nonce: accountNonce,
    // Signed by the EOA's private key
  }],
}
```

The EOA temporarily "becomes" a smart account, executes the batch atomically, and delegation persists (unlike initial proposals where it reverted). The key is that `encodeBatchCalls()` output is identical for Bankr, 7702, and the existing atomic path.
